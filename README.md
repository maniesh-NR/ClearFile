# ClearFile

**A clean-room, demonstration US federal tax-return prototype.** ClearFile is
not IRS-authorized, cannot e-file, and must not be used to prepare a real tax
return. It exists to study — cleanly and reproducibly — what a simplified
TurboTax-class interview-and-calculation flow looks like under the hood, and
to ship that flow to every desktop and mobile platform from a single
codebase.

## Clean-room line

ClearFile reproduces *function and field structure*, never *text, copy, or
expression*. That line is drawn by:

- **17 U.S.C. §102(b)** — the Idea-Expression Dichotomy: methods of
  operation, concepts, and procedures are not copyrightable.
- **The Merger Doctrine** — when an idea can only be expressed in one or a
  few ways, the expression merges with the idea and is unprotected.
- **Scènes à faire** — elements that any implementation of the same
  functional goal must necessarily share (here: the line items and
  calculation order dictated by the IRS's own published forms) are not
  protected.
- ***Computer Associates International, Inc. v. Altai, Inc.*, 982 F.2d 693
  (2d Cir. 1992)** — the Abstraction-Filtration-Comparison test for
  separating unprotectable ideas from protectable expression.
- ***Apple Computer, Inc. v. Microsoft Corp.*, 35 F.3d 1435 (9th Cir.
  1994)** — filtration applied to GUI elements; unprotectable ideas and
  merger/scènes-à-faire elements cannot ground an infringement claim.

Fuller treatment, including the DMCA §1201(f) interoperability research
exemption and the AES-layer handling of modern `.tax` files, is in
[`docs/reverse-engineering-protocol.md`](docs/reverse-engineering-protocol.md)
§2.

## Calculation engines

The repository contains **two independent implementations** (no shared code)
now held to the same behavior by the shared golden fixtures. The Flutter
engine is the reference; the web engine is a line-for-line port of it
(Stage-3 parity, ADR-009).

### Flutter engine — `clearfile/lib/tax/calculator.dart` (TY2025)

The reference model. Implements:

- Five filing statuses with the MFJ / MFS / QSS / Single schedules.
- Standard deduction with the **OBBBA senior deduction** (age 65+).
- Itemized deduction with **SALT 30% phase-down** above the MFJ $550k /
  MFS $275k thresholds (verified against the IRS's published example).
- Qualified-dividends tax bands (0% / 15%) with NIIT.
- **Child Tax Credit** with the $400k MFJ phase-out (exact 5%-of-excess)
  and the refundable ACTC.
- **Other Dependent Credit**.
- Student loan interest deduction with the MAGI phase-out (and the MFS
  exclusion).
- Charitable deduction capped at 60% of AGI.

Every parameter is a named constant with its source cited; every parameter
is pinned by a calculator test that hand-verifies the math. The cross-engine
parity tests pinned to the IRS worked examples are the shared golden
fixtures (`fixtures/tax/`) — landed with the Stage-3 parity set
(2026-11-15).

### Web engine — `src/lib/tax/engine.ts` (TY2025, at parity)

A line-for-line TypeScript port of the Flutter reference engine
(`TaxReturnData` model, same per-status parameters in `config.ts`, same
computation order — including the QDIVCG stacking, the SALT phase-down,
the OBBBA senior deduction, the student-loan phase-out, NIIT, and the
Schedule-8812 exact 5%-of-excess CTC phase-out with next-$1,000 rounding,
all at cent precision). It runs the same 17 shared golden fixtures in CI
(`scripts/web_parity_test.mjs`) — 17/17, zero field failures — and the two
engines read and write the **same unified return file format**: the
versioned `.clearfile.json` envelope (ADR-015), whose `filing` payload is
identical in both codebases, so saved files round-trip across the Flutter
app, the web prototype, and the `.tax`-extension exchange container
(`docs/return-format.md`).

Two scope notes, recorded as debt: the previously projected TY2026
parameters were **dropped** rather than half-supported (parity with a
reference that has no TY2026 parameter set cannot be invented — D32; the
web store and `.cfr` loader migrate old saves to TY2025), and the
whole-dollar display rounding is UI-level only.

## Engine limitations

Both engines are demonstration-grade simplifications; neither is a
form-for-form 1040 implementation. In particular:

- **Both engines (identically, by construction of the parity port)**: some
  parameters and phase-outs are modelled at a summary level rather than
  form-by-form (for example, no AMT, no Schedule SE/self-employment tax, no
  state returns, no estate/trust schedules); phase-outs apply the published
  formulas but do not replicate every worksheet's intermediate rounding;
  the ACTC allocation between CTC and ODC in the partial-absorption zone,
  the student-loan worksheet's three-place rounding, and the marginal rate
  being ordinary-only are deliberately simplified (D31).
- **Web engine only**: TY2026 is not supported (the reference engine has
  no TY2026 parameter set to mirror — D32; old saves are migrated to
  TY2025).
- The web engine's engine-level parity is pinned by automated tests against
  the shared IRS-pinned golden fixtures; the deterministic review layer
  flags missing or inconsistent entries but is not a substitute for review
  by a qualified preparer or IRS-authorized software.

## AI assistant (bring your own free key)

The AI cascade is **opt-in** and **bring-your-own-key**. No keys ship with
the app, no telemetry is sent, and the providers are called directly from
the user's device. In the Flutter app, return figures go to your chosen
provider **only when you opt in** (off by default) — tapping the assistant's
review button shares the same de-identified figures per request. In the
web prototype, the copilot panel always sees the summarized return
(de-identified: no names, SSNs, or employer names — the one exception is
text pasted into auto-fill, which is transmitted to your provider for
extraction).

> **Note on the v1.0.0 release binaries:** the Android and macOS binaries
> shipped with tag `v1.0.0` predate the network permission/entitlement and
> **cannot reach AI providers** — the assistant silently fails on them.
> **Fixed in the v1.0.1 release** (Android INTERNET permission + macOS
> network-client entitlement + the in-app/release network disclosure).

The default chain walks the strongest free tiers top-to-bottom and
auto-degrades on rate limits (429) and auth failures (401):

1. `gemini-3.1-pro-preview` (Google AI Studio)
2. `gemini-3.8-flash` (Google AI Studio)
3. `gemini-3.5-flash-lite` (Google AI Studio)
4. `nvidia/nemotron-3.5-super-vl:free` (OpenRouter)
5. `nvidia/nemotron-3-ultra-550b-a55b:free` (OpenRouter)
6. `openrouter/free` (OpenRouter's own free-pool router)

Old `mistral` entries in a saved settings file are silently dropped on load
— Mistral's free tier ended 2026-09-21. The model chain is fully editable
in-app; see `clearfile/lib/ai/settings.dart` for the
`AiSettings` / `AiModelSpec` / `AiSettingsStore` implementation and
`clearfile/test/cascade_test.dart` for the cascade behaviour contract.

## TurboTax-format bridges (what ClearFile can do with `.tax`/TXF today)

ClearFile's own save format — the **unified return file** (ADR-015) — is
`.clearfile.json`: a versioned envelope (`format: "clearfile-return"`,
`version: 2`) around the shared `filing` payload, written by the Flutter
app (export and autosave) and the web prototype alike, with a **version
guard** on read (future files are refused, never guessed at), migration
with user-visible warnings for the older layouts (the web prototype's v1
`.cfr`, the Flutter app's pre-unification flat layout), and the sealed
import outcome (cancelled / failed-with-reason / ok-with-notes — never a
silent failure). The envelope also rides inside the ClearFile exchange
container's `clearfile.json` entry. Full schema and migration matrix:
`docs/return-format.md`; pinned by 14 Dart tests + the web bridge suite
in CI.

- **Import a TurboTax TXF export** (the documented safe bridge, protocol
  §2.5): the published Tax Exchange Format spec v042 — W-2s grouped by
  copy number, income/dividend/deduction/payment records, honest notes for
  anything outside the demo scope.
- **Inspect a `.tax` file read-only**: ZIP container entry listing, per-entry
  entropy with likely-encrypted flags, recognition of the modern Intuit
  container shape — and an explicit statement that ClearFile does not
  decrypt Intuit files (no keys, no ready-made decryptors; protocol §2.2/§7).
- **Export TXF** (both codebases) to spec v042: per-W-2 copies
  (460/461/466), interest (287), student-loan interest (636), negative
  signs for money paid — verified by `scripts/txf_taxfile_test.mjs` in CI.

## Web demo (GitHub Pages)

The Flutter web build is deployed at
`https://maniesh-NR.github.io/ClearFile/` by `.github/workflows/pages.yml`
(on push to `main` touching `clearfile/`, and via manual dispatch). The
deployed build runs the app **from the browser tab's memory** — returns and
AI settings are not persisted across reloads (the Welcome screen states
this; native builds keep file-backed persistence).

Security-headers disclosure (honest limitation): **GitHub Pages serves no
custom HTTP response headers.** The Stage-4 "security headers pinned"
requirement is therefore met in meta-tag form only — the Content-Security-
Policy and `no-referrer` policy pinned in `clearfile/web/index.html`. The
CSP deliberately allows a little headroom beyond the current bundle:
`script-src`/`connect-src` keep a `www.gstatic.com` allowance (a recorded
choice in `pages.yml` so a future CanvasKit-CDN build needs no CSP edit;
the current bundle ships CanvasKit locally via `--no-web-resources-cdn`)
plus the `'unsafe-inline'`/`'wasm-unsafe-eval'` sources Flutter's bootstrap
requires. Meta CSP cannot carry `frame-ancestors` or `report-uri`; those
protections are absent from the meta layer (the `*.github.io` edge itself
serves HSTS site-wide). All of this is stated, never overstated.

Boot verification: `scripts/flutter_web_smoke.py` serves the built bundle
under the `/ClearFile/` path and checks, in headless Chromium, that the app
boots (Flutter view attached, a drawn non-blank UI, zero page errors) —
the disclaimer copy itself is pinned by the widget suite, and the
screenshot at deploy time is reviewed against the PROD-5 prominence check.

## Maintenance policy (v1.1 and later — Stage 6)

With the v1.1 DoD met ("a reader can verify every number against a cited
IRS source without reading git history" — engine inline citations, the
pinned golden fixtures, and the independent Decimal oracle), the project is
in **declared maintenance mode: parameter corrections only.**

- **Accepted changes:** tax-parameter corrections backed by a cited IRS
  source (flowing through the shared golden fixtures + the oracle, per the
  Stage-3 contract), bug and security fixes with regression tests, and
  dependency security bumps (the `npm audit --omit=dev` critical gate).
- **What earns a v1.x bump:** the above, when user-visible.
- **What earns the v2.0.0 major bump:** only the ADR-017 epilogue — the
  Rust core and per-OS native stacks — or a breaking return-format change
  (which itself requires a new envelope `formatVersion` + migration, per
  the ADR-015 version-guard rule). The web prototype stays in maintenance
  parity (ADR-016) until the Rust core serves the web (WASM) and the TS
  engine retires.
- **Out of scope without a new owner directive:** new engine features, new
  platforms, new web-engine features (the ADR-016 freeze), and the TT
  compatibility program beyond its own gated lanes (ADR-019/020).
