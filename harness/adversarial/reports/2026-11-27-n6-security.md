## Conditions

1. **The alloc/free seam re-specified to a sound, bounded, guarded
   shape.** Measured defect: `clearfile_free` is `CString::from_raw`
   (lib.rs l.541-548) — it reconstructs the allocation by strlen and
   drops a Box<[u8]> of length strlen+1. "A leaked Vec freed by the
   existing clearfile_free" is therefore a mismatched-dealloc (a Vec is
   not a CString); and even the corrected CString-discipline buffer
   (zeroed len+1, NUL at the end) is freed with a wrong reconstructed
   length whenever the caller wrote interior NULs before the terminator —
   and the .tax container payloads this lane exists to carry are ZIP
   bytes FULL of interior NULs (the (ptr,len) input contract is
   explicitly NUL-safe, l.110-118). Requirements: (a) the allocation
   path and the free path must be discipline-compatible BY CONSTRUCTION —
   alloc hands out a buffer obtained through the same CString mechanism
   free expects (a zeroed len+1-byte buffer, NUL at index len), never a
   raw Vec; (b) the interior-NUL dealloc-size mismatch is a RECORDED
   wasm-only hazard: cfg-gate the export to `target_arch = "wasm32"`
   (the N4/N5 native cdylibs keep their export surfaces byte-identical —
   the tightest freeze posture for the already-shipped artifact classes;
   no native consumer can ever hit a mismatched-layout free, which on a
   native allocator is genuine UB), and document in the source that on
   wasm the mismatch is benign because the wasm allocator's free ignores
   the layout (dlmalloc reads its own chunk header) — the honest note,
   never a silent accident; (c) `check_size(len)` (the 512 MiB input
   bound) runs BEFORE the allocation, inside `ffi_guard` (a 4 GiB
   memory.grow failure aborts through handle_alloc_error → a trap; the
   named bound message is the honest refusal); (d) the wasm parity suite
   proves the FULL cycle in node with the interior-NUL class specifically:
   alloc → write container bytes (NUL-bearing) → load_and_compute → free
   → repeat ≥100 iterations asserting NO trap and STABLE
   `memory.buffer.byteLength` (the leak check — a leaking alloc would
   grow wasm memory monotonically; this is the whole point of the export).
   If the orchestrator prefers a host-visible export instead of the
   cfg-gate, the boundary battery's alloc/free test must restrict itself
   to NUL-free payloads on host (where the discipline is sound) and the
   header documents the wasm-only consumer — but the node-side cycle
   proof of (d) is required in EVERY variant. Checkable: the export's

   cycle test exists with the interior-NUL class + the stability
   assertion; the wasm-gated variant shows no native export-list change

## Risks register

1. **The interior-NUL dealloc mismatch (condition 1) rides on the wasm
   allocator's layout-ignoring free.** Benign today (dlmalloc reads its
   own chunk header), but a future std allocator change or a native
   misuse would surface it. Walls: the wasm32 cfg-gate, the honest
   doc line, the node-side cycle test with the container class.
2. **Wasm toolchain drift on the release lane.** The shipped .wasm is
   built by whatever rustc the runner image carries at tag time (no
   1.100.0 pin is possible on the runner without the toolchain-action
   class, which the lanes deliberately avoid); a rustc change could
   alter the shipped engine's bytes/behavior between the suites job's
   proof and the release build. Mitigated (not closed) by condition
   6(b)'s at-build-time parity re-run + the version echo; the residual
   non-reproducibility is the same posture as every other lane — record
   it, don't paper over it.
3. **Blind authoring (the N5 precedent, now wasm-shaped).** No wasm
   build has EVER run here (the sandbox has no wasm std — measured;
   the stray tarball is unextracted material, not a toolchain): the
   first compile IS the CI run, and the four-round N5 CI-fix precedent
   says rounds are likely. Mitigations: the fail-closed guards, the
   wasm parity + cycle + trap suites, the honest CI-fix record.
4. **The loading-gate UX class.** The app gains an async boot
   dependency: a failed fetch (404/corrupt .wasm) or a premature sync
   call must surface a NAMED error in the wording family — never a
   white screen or a silent wrong result; the prerender path (all
   consumers are 'use client' — verified steps/filemenu/ai-ui/page)
   must render the loading state without any wasm call.
5. **The frozen-artifact rot.** The four files stay tsc-checked but
   unreferenced: their COMPILE health is CI-caught forever; their
   PARITY is intentionally no longer pinned (the suites transferred
   off them — that is what retirement means). The banner should say so
   (dead code kept as the study artifact), so a future reader doesn't
   "helpfully" revive them.
6. **Transient 2× memory on large imports.** A big file import holds the
   JS ArrayBuffer + the wasm-side alloc copy transiently (up to ~1 GiB
   at the 512 MiB bound). The named bound refusal before the read is
   the honest UX; the transient cost is recorded, not hidden.
