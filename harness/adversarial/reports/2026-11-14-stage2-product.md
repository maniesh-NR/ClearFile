## Findings

**PROD-1 [MAJOR — Stage-2 definition of done is not honest as written].** ROADMAP.md:144-154: "Time-boxed with its own definition of done: published specs for N formats." **N is defined nowhere** (repo-wide grep: only my own Stage-0 phrasing and ROADMAP's copy of it), and the "time-box" carries no value — no session count, no calendar. Contrast the parity set's concrete two-session box. Agenda item 2 asked directly: is N defined? No. Is the stage actually time-boxed? No. A stage whose done-criterion cannot be counted cannot be gated honestly, and it is the only remaining unbounded stage (Stage 3 got a tripwire; Stage 2 got a placeholder).

**PROD-2 [MAJOR — ordering: swap Stage 2 and Stage 3; settle it here as mandated].** Stage 3 before Stage 2 is the right order. Rationale:
- **No dependency either way**: Stage 3 needs nothing from Stage 2 — TXF is an open, documented format (the protocol's own §2.5 names it the safe bridge), IRS worked examples are public, golden fixtures are Flutter+JSON work; Stage 2's scanners need nothing from Stage 3. The "formats → specs → engine" narrative is the RE leg's *internal* pipeline (protocol §3 Phase 5), not a repo-level prerequisite.
- **Value**: Stage 3 is the self-described highest-value stage and carries the project's definition of done ("v1.1 = a reader can verify every number against a cited IRS source"). Stage 2 is, by my own Stage-0 assessment, a research side-quest whose value to the demo is indirect.
- **Burnout/abandonment**: ADR-009 doubled engine-touching cost. A single maintainer can stop at any time; front-loading value means an abandoned project still delivered the verifiable engine. Stage 3's fixtures-first slice is itself a contained, single-engine, immediately valuable opener — better momentum than an RE-tooling detour.
- **Narrative coherence**: the README's front door is the engine and its limitations ("Cross-engine parity tests… are Roadmap Stage 3"). Shipping the verifiability story *before* adding RE tooling for proprietary formats also answers the demonstration-vs-misuse tension in the right order: the repo's public story when RE content lands is anchored by "here's how to verify every number," not by RE content sitting atop an unverifiable engine.
- Cost, stated honestly: the swap makes the eventual RE-entry gate the third full-depth gate (vs. two if Stage 2 runs now). One extra expensive gate is an acceptable price; every stage keeps exactly one entry gate.

Mechanics: this gate (full-depth, agenda item 3 explicitly reviews the Stage-3 plan) can enter the re-sequenced parity stage directly; ROADMAP, WORKFLOW §2.2 tiering cross-refs, and harness_check's tiering greps must be amended together so the fuller-scope-wins rule and the checker stay green.

**PROD-3 [MEDIUM — the tripwire has no clock].** ROADMAP.md:30-36: "if the box is exceeded or **the Stage-3 gate slips**, the web-freeze option returns to the NEXT gate agenda." "Slips" has no baseline — all dates are session dates and no anchor is defined; under the current ordering, inserting Stage 2 moves the Stage-3 gate by construction, and nothing says whether that counts. What it means for my ordering: under the swap, the clock must be *defined at the parity stage's entry* (baseline = entry session; box = two working sessions on the web parity set; slip = exit gate not convened within a named total-session budget), otherwise the tripwire fires only on goodwill.

**PROD-5 [NOTE — Stage-2 test/fixture design tension that will bite mid-stage if left implicit].** "Unit tests pinned to the tools" + "a CI-checkable no-binary-blob assertion on fixture paths" + §7.2 (decrypted content never committed) are mutually coherent **only if** tool unit tests use synthetic fixtures constructed in code — any committed binary fixture (e.g., an encrypted `.tax`) fails the no-blob assertion by construction. Real-file differential mode must run only on the owner's private corpus, never in CI. Also §7.1 (owner-authored corpus only) is pure policy — the tool should make it friction-y (a required provenance declaration in the CLI/fixture manifest). This is exactly the demonstration-vs-misuse edge; the plan's read-only/write-free/resource-bounded constraints are the right mitigations, but the fixture strategy must be explicit before the stage starts.
