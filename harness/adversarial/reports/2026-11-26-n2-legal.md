## Findings on the mandate's five probes

**(1) The Slint license is real, verified, and genuinely usable.**
slint 1.19's published terms (crates.io metadata, live, both patch
releases) are `GPL-3.0-only OR LicenseRef-Slint-Royalty-free-2.0 OR
LicenseRef-Slint-Software-3.0`, and the crate tarball ships the full
license texts. The GPL branch is the standard GPLv3 (no rider), and the
FAQ's own guidance ("if your app is open source, use the GNU GPLv3")
matches this GPL-3.0-only project exactly: the combined binary is
GPL-3.0, and no additional terms attach — the attribution-badge /
AboutSlint obligations belong to the royalty-free branch only, which
this project does not elect. **No component is separately licensed**:
all 15 first-party crates (every crate the app can pull: runtime,
backends, renderers, the `.slint` compiler, the proc macros,
`slint-build`) carry the identical triple license, so the GPL election
covers the whole stack uniformly — including the macro/build path and
the `.slint` language tooling (the language itself is not separately
licensed; there is nothing to license there). The "IDE-licensed"
components (`live-preview`, `mcp`) are opt-in features under the same
triple license and are not in the default set. The "palette" is not a
Slint thing at all (verified: no MCU vendoring anywhere in the crates).
The premise of ADR-017's annex ("Slint under its GPL-3.0 option") is
factually confirmed. What is missing is the **election record**: the
OR means downstream choice must be made once and recorded in-tree,
because a bare third-party root dependency living unattributed in a
GPL-3.0-only tree invites the wrong question later.

**(2) The palette port is the first third-party-derived material in
`core/` and owes the Apache-2.0 derivative posture.** The D44 port
("ported from the Flutter framework's bundled material_color_utilities,
verified by a fixture corpus generated by a tracked Dart tool against
the pinned SDK") is a **translation** — the classic derivative work — of
Google's Apache-2.0 code (the pinned 0.13.0 LICENSE verified), not a
vendoring and not a clean-room spec reimplementation: the tonal-palette
contract (HCT/CAM16 math, tone mapping, chroma capping) lives in
Google's code, not in a published standard. Apache-2.0 is one-way
GPL-3.0-compatible, so relicensing the port into a GPL-3.0-only
`core/src/palette.rs` is lawful; what Apache-2.0 §4 requires is notice
discipline: the derivative file must state its provenance and changed
status, and recipients must be able to get the Apache-2.0 text (there is
no NOTICE file upstream, so that obligation is vacuous). The honest
posture — and it is owed by this repo's own standard, not just the
license — is: a provenance doc-comment in `palette.rs` (upstream,
version, copyright line, port-not-vendored), and a
`THIRD-PARTY-NOTICES.md` entry (the file's charter literally covers
"third-party material included in the tree"; a hand-written port is
included material in derived form). This also keeps the record honest:
the N1-exit finding "the delta introduces no third-party material" was
true then and is superseded now — silently absorbing Google's
expression into an all-first-party GPL-3.0-only tree would be exactly
the drift the notices file exists to prevent. The ADR-017 MD3 note
("unprotectable functional design, *Apple v. Microsoft* filtration")
remains correct for the DESIGN language and the algorithm as method;
it does not license copying Google's CODE expression — the two
statements coexist only if the attribution lands with the port. The
fixture corpus itself is clean: seed→palette values are unprotectable
facts, and generating expected values by running the reference library
is the D43-differential pattern (the reference is the expectation by
design), not a fixtures/tax annex-(d) violation — but the corpus README
must say which reference and which pin.

**(3) The manifest timing: deferral is the recorded rule; the proxy
holds only while nothing is distributed.** ADR-017 l.545: "A
per-platform LICENSES manifest lands with each platform's first tagged
release." The N2 delta ships no tag (the v2.0.0 rule, l.516, makes the
first native GA the trigger), so deferring the Linux manifest is not a
loophole — it is the recorded rule, twice-read into prior gate records
(N1-exit risk (b); stage-2 LEGAL-3). The counsel nuance that must be
recorded: GPLv3 §4/§6 obligations attach at **conveyance**, and a
"tagged release" is only the project's proxy for conveyance. The proxy
holds only as long as no built binary reaches anyone before the first
tag — which is why condition 8 exists (GitHub Actions artifacts on a
public repo are downloadable by any authenticated user; today the
workflows upload no app binaries, and that must stay true for the
unreleased native app).

**(4) Disclaimers: the disclosure surface follows the product, not the
platform.** The web/Flutter apps carry three surfaces: the in-app demo
disclaimer (welcome.dart l.85–103: "Demonstration software … not
IRS-authorized, cannot e-file, must not be used to file a real tax
return"; README "Demo disclaimer" section), the D12 AI privacy
disclosure pair (disclosure.dart — which describes provider calls this
app cannot make), and the non-affiliation strings (pinned IN the core,
carried automatically). The native app is the same product; if its MD3
window renders product surfaces, the demo disclaimer belongs in-window
(and in any results-printing text mode), stated as the same facts with
platform-idiomatic wording. The AI-absence note is the mirror problem:
the native build contains no AI and performs no network access at all,
so (a) it must NOT import the D12 disclosure (which would describe
nonexistent behavior), and (b) where a user would look for the
assistant, the honest surface is an affirmative absence statement —
the same disclosure discipline D12 established ("single source of truth
… so the copy cannot drift from the behavior"). No release page is owed
until a tag exists.

**(5) cargo-deny from the compliance side: real tool, closed allow-list,
recorded election, same-commit timing.** The recorded trigger ("a real
cargo-deny in the same commit as the first external dependency") is
satisfied by the proposal's shape: apps/linux's first commit introduces
slint, so the real check lands in that commit. Mechanism: both recorded
options remain valid (N1-entry LEGAL-2: "cargo install or a SHA-pinned
action"); a homegrown scan script is NOT acceptable — the exact hard part
is SPDX OR-expression semantics with `LicenseRef-*` ids (cargo-deny's
documented evaluation passes "GPL-3.0-only OR LicenseRef-…" via the
allowed `GPL-3.0-only` branch; a naive script either fails the Slint
crates or, worse, allow-lists the whole OR). If the action is used it
must be 40-hex-SHA-pinned per D10 (the standing rule, done for existing
`uses:`); if `cargo install` is used, the version must be pinned
(`--locked --version x.y.z`). Config content (honesty for the hundreds
of transitive licenses): a **closed allow-list** where every id is
GPL-3.0-only-compatible — `GPL-3.0-only` (the election), MIT,
Apache-2.0, BSD-2/3-Clause, ISC, Zlib, Unicode-3.0/Unicode-DFS-2016,
0BSD, CC0-1.0 as actually encountered; `GPL-2.0-only` and unlicensed
are barred structurally (v2 denies everything unallowed), GNU handled
pedantically (`GPL-3.0-only` exactly, not deprecated `GPL-3.0`);
**the two Slint LicenseRefs must NOT be added to the allow-list** —
allowing them would license the project under terms it has not elected
(attribution obligations it is not meeting); the crates pass via the
GPL branch and that election is stated in a config comment; build-deps
must stay checked (`slint-build` compiles the `.slint` and embeds
Slint code into the binary); per-crate `exceptions` (with a recorded
reason), never global widening, for any surprise.

## Risks register

(a) **LicenseRef/OR evaluation drift**: cargo-deny's closed-allow-list
OR satisfaction is documented but version-sensitive (the 0.18.4 GNU
pedantics change is a live example of semantics moving); the
live-green first run (condition 5) is the tripwire, and the core's
zero-dep assertion is untouched as the second layer. (b) **The
material-style widget icons** bundled in `i-slint-compiler` (compiled
into the app binary) are Google-Material-Symbols-geometry SVGs with no
in-crate third-party attribution — Apache-2.0 is one-way GPL-compatible
so there is no conflict, but the per-platform Linux manifest at first
release should attribute the embedded widget assets honestly (Slint's
own compliance posture is not the project's to fix, but the project's
manifest must describe its own binary truthfully). (c) **The GPL §6
release-body sentence goes stale at first native release**: "the
complete corresponding source … is the tagged public commit" is exactly
true today (binaries built from in-repo sources) and becomes loose
once a native binary embeds crates.io-sourced code — extend it at the
first native GA ("the tagged commit plus the exact crate versions
pinned in Cargo.lock, sources available from crates.io") so the release
page does not overstate §6 compliance. (d) **Slint version drift**:
1.19.1 landed 2026-11-24; minors are frequent and a future major could
change licensing — the lock pins exactly and every cargo-deny run
re-verifies, so the check is the standing tripwire. (e) **Retrospective
manifest consistency**: the web/Flutter releases predate the
per-platform manifest rule's forward application; when the first Linux
manifest is authored, sanity-check whether the already-shipped Flutter
zips' bundled-license coverage (Flutter build outputs) satisfied the
rule's spirit, and record the answer rather than leaving the asymmetry
unexamined. (f) **Palette translation depth**: if the tonal-palette
contract requires the HCT/CAM16 solver (not just tone tables), the
translation surface into `core/` is large — the fixture corpus is the
right guardrail; keep code independently expressed where the model is
published science, and never paste Google's code comments wholesale.
(g) **Working-tree drift at review time** (package.json/package-lock.json
modified, uncommitted — not mine, not the proposal's): an environment
artifact the orchestrator should reconcile or confirm before the gate
closes, since the recorded review premise said "tree clean".

## Non-binding advisories

1. `apps/linux/Cargo.toml`: `publish = false` (matches the core; no
   crates.io distribution surface for a demo app).
2. Do not enable the `live-preview` or `mcp` slint features — IDE
   machinery, unused in a shipped binary, and the slimmer the feature
   set the smaller the license/manifest surface that must be verified.
3. Consider a one-line `THIRD-PARTY-NOTICES.md` Slint row at first
   commit (election + pinned version) even though the full per-platform
   manifest defers — it is the same honesty pattern as condition 6 and
   costs one line.
4. Use `cargo deny list licenses` output as the generator/starting point
   for the eventual Linux LICENSES manifest (the digest discipline that
   made the differential corpus cheap to audit).
5. The Stage-2 slip re-agenda (T3 keystream chase / tax-modern.md /
   RE-protocol namespace rule) stands as recorded — nothing in the N2
   delta touches the RE protocol or its DMCA §1201 posture; re-surface
   the owner's three options (fund T3 / supersede the namespace rule /
   default re-agenda) rather than defaulting silently.
6. Keep the two MD3 statements from drifting apart in future records:
   the design language is unprotectable (annex; *Apple v. Microsoft*
   filtration) and nominal references carry no Google/Material logos —
   but Google's palette CODE is protected expression riding the
   Apache-2.0 path; the notices entry is what makes both statements
   true simultaneously.

**Summary:** The proposal's licensing spine is factually sound and
verified live end-to-end: Slint 1.19's published terms are exactly the
triple license with a rider-free standard GPL-3.0-only option, uniform
across every crate the app can pull, with no separately-licensed
palette/IDE/language components and a default feature set that is all
permissive downstream; the GPL election fits this GPL-3.0-only project
with no attribution obligation. The gaps are record-keeping honesty,
not legality: the election and the toolkit consolidation must be
recorded (the annex's own words), the D44 palette is the first
third-party-derived material in the core and owes the Apache-2.0
derivative posture (provenance comment + THIRD-PARTY-NOTICES entry),
cargo-deny must be the real closed-allow-list tool in the same commit
as slint with the LicenseRefs deliberately absent from the allow-list,
the in-app demo disclaimer and a truthful AI-absence note follow the
product into the native window, and the manifest deferral holds only
while no binary is conveyed. Eight checkable conditions; nothing
block-worthy.
