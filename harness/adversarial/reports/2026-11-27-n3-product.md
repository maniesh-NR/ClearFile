# ADV-PROD — N3 delta-scoped gate (2026-11-27, Task N3-GATE-PROD)

**Scope:** the N3 delta-scoped gate (the Android native UI over the Rust
core; ADR-017's epilogue, third stage), ADV-PROD lane — roadmap rightness,
stage discipline, the working-app bar, single-maintainer sustainability,
records honesty. The proposal under review: (1) a new separate-root
`core-ffi/` crate (`clearfile-core-ffi`, publish=false, clearfile-core as
a path dep, core/Cargo.lock untouched) carrying the ONE flat C ABI
(`extern "C"`, cbindgen-generated header — N3 is the recorded first-FFI-
consumer trigger), the cdylib, and the thin Android JNI shim; (2)
`apps/android/` — Kotlin KMP-shaped with exactly ONE target (Android
Views, no Compose), a viewer demo in the apps/linux pattern (bundled
golden fixture + SAF open of `.clearfile.json`/`.tax`, compute via JNI,
MD3-from-seed theme via the palette FFI at the shared corpus seed, the
honesty surfaces); (3) verification via local host FFI tests + a CI
android job (cross-build cdylib, gradle, JVM unit tests loading the host
.so through JNI asserting golden-fixture parity), nothing uploaded;
(4) the ENG/SEC riders (duplicate-scan bound + file-size pre-check) land
in this delta; (5) a two-session box with intra-session checkpoints;
(6) the variant preconditions (zero `clearfile/`+`src/` paths,
release.yml byte-unchanged, no version movement, nothing shipped).
Pushed tip `44929c0` verified; the working tree clean — verified live
by my own `git status --short` (empty). The proposal is honest against
the record on every mandate point: the scope matches the settlement's
stage bar as the N2 precedent defined it (a labeled viewer demo), the
FFI seam matches ADR-017's recorded design exactly, the riders land per
the standing "closure before any FFI wiring, and N3 IS the FFI wiring"
framing, and the preconditions match the standing discipline. My
findings are refinements, not blockers: the working-app claim needs its
verification lanes named (a CI lane stopping at `compileDebugKotlin`
leaves the installable APK unproven — the box must include an APK
assembly), the KMP claim needs a shape-matches-record rule, the disk
reality (measured **1.8 GB** free, not the brief's ~5 GB) forces the
CI-primary posture for the app session, and the standing duties (the
slip's fifth surfacing, the N4/N5/N6 pre-positioning, the bookkeeping
set) are bound into the gate record as conditions. The per-OS order
STANDS (N3 → N4 → N5 → N6; re-settable at the gate, no product demand
to re-order — no new measured facts favor N4-first, and Android's
user-base-first rationale plus the shipped-v1.x-APK lineage are
unchanged), and the v2.0.0 discipline holds (nothing at N3 ships; the
epilogue's own terminal freeze is N6's to declare).

## Risks register

- **CI-only Android iteration** — no local SDK/gradle/Kotlin (all
  re-measured absent) and the fetcher class disk-blocked at the
  measured 1.8 GB: every compile is a blind push→wait→inspect round,
  and the N2 CI fix took four rounds WITH local builds working.
  Mitigation: Condition 6's red-close absorption + Condition 3's
  per-lane status wording; the JVM-tests-through-the-real-.so design
  is the right seam (it exercises exactly what local testing cannot).
- **The JNI symbol-mangling class** — `Java_`-mangled exports vs the
  JVM's lookup is the classic multi-round flake source; the host-.so
  JVM parity tests catch it in the same CI lane, and the header/shim
  split keeps the C ABI the audit surface.
- **KMP claim/shape drift** — a plain module landed while the records
  still say KMP (or a `:shared` module landed with the README calling
  it "plain Android"). Mitigation: Condition 2's shape-matches-record
  rule, checked at the exit gate.
- **The third-engine risk** — engine logic accreting into the `:shared`
  Kotlin module (the natural gravity of a "shared" layer). Mitigation:
  Condition 2's zero-engine-logic rule + the exit gate reviewing the
  module's contents (compute only through JNI).
- **Compile-only verification gap** — an APK that was never assembled
  being recorded as a "working app". Mitigation: Condition 3(i)'s
  assembleDebug requirement.
- **The slip's indefinite parking** — the count-drift risk (the
  2026-11-27 entry self-labeled "fifth surfacing"; this gate's
  restatement is the one that entry said rides with N3's gate); the
  proof of the pattern would be a cycle without an owner word.
  Mitigation: Condition 4's pinned count.
- **macOS runner availability drift before N5** — the macos-13 image's
  retirement window is exactly the deployment floor's CI coverage;
  HEAD-probes prove reachability only. Mitigation: Condition 5(b)'s
  live-verification list at N5's gate.
- **Disk moving under the box's feet** — ~3 GB consumed between the
  2026-11-27 close (~5 GB) and this gate (1.8 GB); the FFI session fits
  but the record must re-measure at each session start (ENG's plan,
  named here because a mid-session ENOSPC is a logged-slip risk, not a
  silent one).
