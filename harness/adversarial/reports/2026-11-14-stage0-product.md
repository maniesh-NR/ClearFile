# ADV-PROD — Product Strategist / Roadmap · Stage-0 review (2026-11-14)

**Scope reviewed (read-only):** `README.md`, `harness/*` (all seven docs + `scripts/sandbox_backup.sh`), `docs/reverse-engineering-protocol.md`, both implementations' engines/config/UI (`src/lib/tax/`, `src/lib/files/`, `clearfile/lib/`), `.github/workflows/release.yml`, git state (`git log`, tags, tracked files), actual test counts.

## Findings

**1. [CRITICAL] Two divergent engines live under one README claim — the artifact's flagship trust statement is false for the web half, and no roadmap stage resolves it.**
Evidence: `README.md:51-70` — "The engine in `clearfile/lib/tax/calculator.dart` (and `src/lib/tax/` for the web prototype) implements: … SALT 30% phase-down … Qualified-dividends tax bands (0%/15%) with NIIT … OBBBA senior deduction … student-loan interest …" But `src/lib/tax/engine.ts:8-13` explicitly disclaims it: "No qualified-dividend / capital-gain preferential stacking … No NIIT, AMT…"; `src/lib/tax/engine.ts:107-113` sums `taxPaid` into itemized deductions with **no SALT cap at all**; `src/lib/tax/config.ts` (`YearConfig`) has no SALT/senior/QDI/NIIT fields. Further divergence: web supports **TY2026** vs Flutter TY2025-only; CTC phase-out modeled differently (`engine.ts:125-127` dollar-per-$1,000 units vs `calculator.dart:114` 5%-of-excess-AGI); even the parameter provenance chains differ (web cites NTU/CPA Practice Advisor/Fidelity; Flutter cites IRS VITA/Tax Foundation/i1040gi).
Why it matters: the project's stated reason to exist is to let someone study a TurboTax-class engine "cleanly and reproducibly." A public README overstating what the artifact computes is precisely the trust failure this repo exists to avoid — and it is the first thing a student will read. Structurally, the roadmap never decides which codebase each stage targets, so every engine-touching stage silently doubles in cost or ships half-done. This is also the project's core sustainability risk: 6 platforms × 2 codebases, single maintainer.
Recommended fix: (a) Correct README **now** — describe each engine's actual scope separately, including a real "Engine limitations" register. (b) Make the two-codebase policy a binding Stage-1 item recorded as an ADR: either **freeze the web prototype** as a first-generation study artifact (docs-only maintenance; README says so; web items removed from Stages 3-5) or commit to **feature parity** (missing web engine features added to the roadmap; Stage-3 parity tests explicitly covering both engines).

**2. [MAJOR] Undocumented product asymmetries make Stages 3-5 unactionable as written.**
Evidence: TXF export exists **only** in the web app (`src/lib/files/txf.ts`, wired at `filemenu.tsx:117-118`, `steps.tsx:626-627`; case-insensitive grep for TXF across `clearfile/` returns nothing). Native save formats differ: `.cfr` on web (`src/lib/files/cfr.ts`) vs `.clearfile.json` on Flutter (`clearfile/lib/io/files.dart:8-12`). The web app alone ships a `.tax` inspector and exchange container (`src/lib/files/taxfile.ts`) and TY2026. Flutter interview is 5 steps (`interview.dart:11-12`) vs README's 7-step web flow. Yet `ROADMAP.md:66-73` says "verification suite for the existing TXF exporter" and "`.clearfile.json` schema versioning + migration" without naming which implementation; `.cfr` is mentioned in no stage at all.
Why it matters: a stage plan that doesn't name its target codebase cannot be gated checkably — "verify the existing TXF exporter" is ambiguous when only one of two products has one, and two native formats with no unification plan is permanent drift.
Recommended fix: add a per-stage implementation-target matrix (web / Flutter / both) to `ROADMAP.md`; Stage 3 either unifies the save format (pick `.clearfile.json` everywhere, migrate `.cfr`) or declares the web prototype frozen.

**3. [MAJOR] The append-only session log pre-records events that have not happened — the audit trail states outcomes before they exist.**
Evidence: `harness/memory/SESSION_LOG.md:46-51` — "Stage-0 adversarial gate convened: … Reports filed under `adversarial/reports/`; consensus in `adversarial/CONSENSUS.md`" and "Closing action: event-driven backup push (first execution…)". Actual state: `harness/adversarial/` contains **only** `ROLES.md` (no `reports/`, no `CONSENSUS.md`); `git status` shows `harness/` and `scripts/sandbox_backup.sh` still untracked (no backup push yet); `ROADMAP.md:21` points Stage-0's gate status at a `CONSENSUS.md` that does not exist.
Why it matters: the harness's entire value proposition is a trustworthy durable record. Entries written before the fact convert the log from evidence into narrative. If this gate returns BLOCK or conditions, the log has already "recorded" success — and `WORKFLOW.md §3` itself specifies appending at teardown.
Recommended fix: append session-log entries only after actions complete, or mark anticipated items `PLANNED` and append the outcome separately; create `CONSENSUS.md` with the actual verdicts as this gate's closing action; reconcile the existing entry with an appended correction note (append-only, never rewritten).

**4. [MAJOR] README truth drift — three concrete inaccuracies in the public artifact's front door (beyond the engine claim in F1).**
Evidence: (a) `README.md:23` documents "`download/` | Pre-built release bundles … for the current tag" — but `download/` is gitignored and untracked (`git ls-files download` → empty); a cloner cannot have this directory. (b) `clearfile/lib/tax/calculator.dart:15` refers readers to "the README 'Engine limitations' section" — no such section exists (grep: not found; README has "Demo disclaimer"). (c) `README.md:20` claims "20 calculator" tests; `calculator_test.dart` contains 19 `test()` declarations; the stated breakdown sums to 43 while the stated total (42) is correct only because the actual count is 19+8+9+3+3.
Why it matters: for a demo with no telemetry and no support channel, README accuracy *is* the product's trust surface. Stage 1 is literally named "Hardening & trust" and does not include a README truth sweep.
Recommended fix: 15-minute sweep: drop/replace the `download/` row with "release assets live on GitHub Releases"; create the real "Engine limitations" section (doubles as F1's fix); correct the test-count breakdown.

**5. [MAJOR] Missing stage: nothing on the roadmap serves the stated audience — no study-facing documentation and no correction channel.**
Evidence: `docs/` contains only `reverse-engineering-protocol.md` and `blueprint.pdf`. `README.md:3-8` defines the purpose as *studying* the flow. Parameter provenance is exemplary but locked in code comments (`tax_year.dart:17-29`). There is no `docs/engine.md` mapping calculator lines to Form 1040 lines, no guided tour of the repo, no in-docs omissions register. `.github/` contains only `workflows/` — no issue templates, no CONTRIBUTING, no "report a wrong number" path.
Why it matters: the artifact is overbuilt on packaging (8 release binaries, 6 platforms) and underbuilt on the one thing its purpose names — being studied. With telemetry rightly absent, the only quality signal available is reader-reported discrepancies against cited IRS sources, and there is no mechanism to receive them. This is what replaces measurement for a demo project, and it is missing.
Recommended fix: add a study-artifacts scope (its own small stage, or folded into Stage 3): `docs/engine.md` (1040 line mapping + limitations register), a 10-minute guided tour (README → calculator → tests), engine-discrepancy and doc-correction issue templates, and an explicit project **definition of done** (e.g., "v1.1 = a reader can verify every number against a cited IRS source without reading git history; thereafter parameter-correction maintenance only").

**6. [MAJOR] The governance process is uncalibrated to project size — four full-repo comprehensive reviews per stage for a single maintainer's demo.**
Evidence: `WORKFLOW.md:69-78` requires each reviewer to examine "all work completed since the last gate, **the whole current repository state**, and the stage plan"; `ROLES.md` defines 4 roles; `ROADMAP.md` carries 5 remaining stages; `WORKFLOW.md` adds discretionary spot reviews with the same mechanics.
Why it matters: that is 20+ comprehensive reviews for stages whose deliverable is sometimes a CI fix (Stage 1) or an AppImage (Stage 4). The two predictable failure modes — the ceremony gets quietly abandoned (the harness becomes aspirational, which is exactly what the owner's durability goal cannot afford), or reviewers rubber-stamp to end the meeting — both defeat the stated goal. The mechanics themselves are good (independence, checkable verdicts, non-silent BLOCK override); the *cost curve* is not.
Recommended fix: tier gate depth in `ROADMAP.md`: full-depth full-repo gates where risk concentrates (Stage 2 RE posture — already ADV-LEGAL-weighted — and the Stage-1 history-rewrite decision); delta-scoped gates elsewhere ("delta since last gate + named risk surfaces"), independence always. Add a tiny self-enforcing check (`scripts/harness_check.sh`): CONSENSUS.md gate statuses match ROADMAP.md, SESSION_LOG's last entry post-dates nothing unpushed — making the harness checkable rather than aspirational.

**7. [MAJOR] Stage 1 contains an internal sequencing contradiction: history rewrite and release integrity in the same stage.**
Evidence: `ROADMAP.md:28-47` puts "History hygiene decision … this invalidates `v1.0.0`'s SHA" and "Release integrity: SHA256SUMS …" in one stage; annotated tag `v1.0.0` → `13205da` exists with 8 assets already published; full-history secret scan already came back clean.
Why it matters: publishing checksums/attestations for assets whose tag you may simultaneously rewrite orphans the trust artifact mid-stage. And the rewrite buys little: anyone who cloned already has the old history; the scan found no secrets; the scaffolding is inert. Meanwhile a public history rewrite on a v1.0.0-ed repo is itself a legitimacy cost for a project whose currency is reproducibility.
Recommended fix: decide rewrite-vs-accept as the **first** Stage-1 item, before any checksum work. Recommended default: accept-and-document (ADR). Rewrite only if a concrete leak appears; if ever done, re-tag and re-release v1.0.1 with sums.

**8. [MINOR] Stage 5 defers an in-app privacy disclosure that belongs in the trust stage — the feature it discloses shipped in v1.0.0.**
Evidence: `ROADMAP.md:82-86` schedules "in-app privacy disclosure tied to the actual transmission behaviour" last; but `welcome.dart:167-174` already asserts privacy claims in the shipped app, and transmission is nuanced: return figures go to third-party providers only when `sendReturnContext` is enabled.
Why it matters: Stage 1 is named "Hardening & trust" — a shipped feature's disclosure is a trust deliverable, not a future one; users of the v1.0.0 binaries live with the current wording for the whole roadmap.
Recommended fix: move the privacy/transmission disclosure (and the settings-toggle labeling) into Stage 1; leave injection suites and fixture e2e in Stage 5.

**9. [MINOR] Stage 4 is packaging breadth as a vanity metric for a demo with no distribution need.**
Evidence: `ROADMAP.md:75-80` (AppImage; `.aab` "Play-ready, unsigned until an account exists"; GitHub Pages) vs `README.md:3-8` (audience: people studying a demo) and no store account, no telemetry, no support channel anywhere.
Why it matters: an `.aab` for a hypothetical account and a second Linux packaging format are speculative work serving no named reader. The single genuinely audience-serving item is GitHub Pages — today the README's only demo path is "clone + build".
Recommended fix: keep and promote GitHub Pages (arguably into Stage 1 or 3 as the demo-distribution channel); cut AppImage/`.aab` to an explicit backlog with a revisit trigger ("a real distribution need appears").

**10. [MINOR] The app-level README is untouched Flutter counter-template boilerplate.**
Evidence: `clearfile/README.md:1-17` — "A new Flutter project … Write your first Flutter app …"
Why it matters: a student browsing the repo's app directory — the directory the whole project is about — lands on template text.
Recommended fix: five-line real README (what the app is, demo disclaimer, test/build pointer to the root README).

**11. [NOTE] The roadmap has no terminal condition or version policy.**
Evidence: `ROADMAP.md` ends at Stage 5 PENDING; no maintenance/sunset policy, no rule for when v1.1 happens or what earns a major bump.
Why it matters: a demo project without a "done" invites an infinite roadmap — precisely where single-maintainer burnout concentrates. Fix: add a closing "Freeze & codify" stage (final study docs, declared maintenance mode: parameter corrections only). Pairs with F5's definition-of-done.

**12. [NOTE] What is sound and should stay.**
The Flutter engine is a genuinely strong study artifact: 19 calculator tests each hand-verifying a named rule, parameter provenance cited per constant, disclaimers placed everywhere a user could act, and no print/PDF path that could be mistaken for a real filing — a defensively good choice. The harness itself is well-built: `sandbox_backup.sh` has a real secret guard, a clean-tree no-op, and a never-silent push failure; `STATE.md`'s hard-won quirks list is exactly the durable memory this project needs; the session log honestly records its own mistakes. Stage 1's technical items are real, not invented. Hardening-first ordering is right for a public repo with known history debt and unsigned binaries. Stage 3's own self-description — engine parity tests against IRS-published worksheet examples as "the highest-value trust artifact this repo can offer" — is the single most product-correct sentence in the roadmap.

## Roadmap assessment

- **Stage 0 (harness): KEEP.** Deliverables are real and mostly sound; gate is in progress. Conditions: reconcile the pre-recorded log (F3), create `CONSENSUS.md` with actual verdicts, add the self-check tooling (F6).
- **Stage 1 (hardening & trust): KEEP, re-scope and re-sequence.** Insert as first items: the two-codebase policy decision (F1) and the history rewrite-vs-accept decision (F7), then README truth sweep (F4) and privacy disclosure moved in from Stage 5 (F8), then CI/tests/types. "Scheduled gitleaks is repo hygiene, not sandbox backup" is a defensible reading of the no-cron directive — keep.
- **Stage 2 (RE infrastructure): KEEP but reposition.** It is a research side-quest, not product work; its value to ClearFile-the-demo is indirect — the protocol itself says TXF and printed PDFs are the safe bridges for data. Time-box it with its own definition of done (published specs for N formats). Decide **repo placement first**: a repo whose public story is "GPL-3.0 demo tax app" hosting RE tooling for proprietary formats muddies both stories; a separate research repo linked from `docs/` keeps the clean-room narrative clean. ADV-LEGAL weighting is already right.
- **Stage 3 (clean-room bridges): KEEP — this is the roadmap's highest-value stage for the stated purpose.** Amend: per-stage implementation targets (F2), save-format unification, and fold the study-guide documentation here (F5) so the trust artifacts are readable, not just present.
- **Stage 4 (platform reach): CUT to "GitHub Pages deploy."** Promote it; it serves the audience. AppImage/`.aab` to backlog (F9).
- **Stage 5 (AI hardening): KEEP, minus the privacy disclosure** (moved to Stage 1). Injection suite + recorded-fixture cascade e2e is the correct remaining scope.
- **MISSING from the roadmap:** a study-artifacts/documentation scope and reader correction channel (F5); a terminal freeze stage + definition of done (F11); harness self-enforcement check (F6).

## Verdict

Stage-0's own deliverables (harness + backup rule + panel) are sound; the roadmap as drafted may not start Stage 1 unamended. Conditions, all checkable before Stage-1 work begins:

1. `README.md:51-70` rewritten to describe each engine's actual scope; the web/Flutter asymmetries of F1/F2 either fixed or explicitly documented as a frozen-web divergence — including the incorrect `download/` row (`README.md:23`), a real "Engine limitations" section (or the `calculator.dart:15` reference fixed), and the test-count breakdown corrected (19, not 20).
2. An ADR in `harness/memory/DECISIONS.md` deciding the two-codebase policy — web-prototype freeze or feature-parity — and `ROADMAP.md` Stage 1 amended to carry that decision as its first item.
