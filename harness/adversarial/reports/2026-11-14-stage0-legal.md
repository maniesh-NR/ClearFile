# ADV-LEGAL — Counsel / Compliance · Stage-0 review (2026-11-14)

**Scope note:** this is a compliance risk review by an adversarial reviewer, not a legal opinion; any §1201 workstream beyond Stage 2 should get licensed counsel (the blueprint itself already contemplates "Counsel sign-off" — `scripts/generate_blueprint.py:852-856`). All evidence was read from the working tree and full git history of `/home/z/my-project` (read-only; no files were created or modified).

**Sound posture (stated up front):** the clean-room expression line is genuinely honored — no copied marketing copy, form-line text, or vendor expression anywhere in `clearfile/lib/` or `src/` (findings 11–12); the RE protocol's §2 legal framework is accurate and its "no key material in repo" claim is *verified true across the entire history* (my full-history scans for `github_pat_`, `AIza…`, `sk-…`, PEM blocks, 32+ char hex blobs: zero hits); LICENSE is the canonical GPL-3.0 text (35,149 bytes); the event-driven backup design (no cron, fast-forward-only push, clean-tree no-op) is legally sensible for a public repo.

## Findings

1. **[MAJOR] An unrelated app (`nitro_nissi`, ~90 files) is published inside ClearFile's public git history at tag `v1.0.0`.**
   - Evidence: `git ls-tree -r 13205da --name-only | grep "^download/"` → 90 files under `download/nitro_nissi/` (full Flutter app: `lib/core/tax/engine.dart`, `lib/core/io/importer_tt.dart`, `lib/core/io/ole_cfb.dart`, i10n, tests…); tag `v1.0.0` points at `13205da` (`git show v1.0.0`); the same tree also carries `.env` (`git show 13205da:.env` → `DATABASE_URL=file:/home/z/my-project/db/custom.db`, benign) and `db/custom.db`. Commit `df617e8` untracked them from HEAD, but history before it — including the tagged release commit — retains everything; `harness/memory/STATE.md:18-23` admits this. The in-history `download/nitro_nissi/pubspec.yaml` self-describes as "Nitro Nissi — a clean-room, open-source guided tax preparation app… GPL-3.0. Not affiliated with Intuit/TurboTax or the IRS", yet its subtree ships **no LICENSE file**, and `importer_tt.dart:2-12` references `docs/FILE_FORMATS.md` / `docs/REVERSE_ENGINEERING_PLAN.md` that are **not present in the tree**.
   - Why it matters: (a) If this is not the owner's own code, ClearFile's public repo is redistributing a third-party work with no in-tree license or attribution — a GPL notice-compliance and misattribution problem, and a copyright-infringement risk if its provenance claim is wrong. (b) Even if owner-authored (likely, given sandbox origin), the public ClearFile repo silently distributes a second complete application that `README.md` never mentions, under a root LICENSE the nested app never references — confusing what anyone is downloading "as ClearFile" and muddying the clean-room narrative. (c) Its importer code (`importer_tt.dart`, `ole_cfb.dart`, `tax_file.dart`) is RE-adjacent content now permanently in-tree.
   - Recommended fix: Stage 1 must make this a **provenance question first, hygiene question second**: (i) record in `harness/memory/DECISIONS.md` whether the owner authored nitro_nissi; (ii) if owner-authored → accept-and-document (NOTICE paragraph in README) *or* rewrite; if not, rewrite is required, preserving public retrieval of the exact source tree the v1.0.0 binaries were built from (GPL §6 corresponding source).

2. **[MAJOR] The Flutter AI-review path transmits dependent names and W-2 employer names, contradicting the app's privacy copy.**
   - Evidence: `clearfile/lib/ai/assistant.dart:97-124` — `buildReviewPrompt` serializes `w2s[].employer`, and `dependents[].name/age/relationship/qualifyingChild` into the outgoing user message; `clearfile/lib/ui/app_state.dart:170-180` — `runAssistantReview` always sends it; the only gate, `systemPromptFor` (`assistant.dart:36-37`), applies to the *system prompt totals*, not this user message. Contradicted copy: `clearfile/lib/ui/screens/settings.dart:105-110` ("totals like AGI and taxable income **(never names or SSNs)**"), `clearfile/lib/ui/screens/welcome.dart:168` ("Your data stays on this device"), the blueprint's shipped claim (`scripts/generate_blueprint.py:782-784`: "sends de-identified summaries that **never contain names**, SSNs, or addresses"), and `README.md:71-75`.
   - Why it matters: the privacy disclosure materially misstates what leaves the device on a stock tap of "Ask the AI assistant to review" (`results.dart:293-304`). Aggregate financial figures were disclosed; personal identifiers were not.
   - Recommended fix: gate the personal fields of `buildReviewPrompt` on `sendReturnContext` (or strip dependent names/relationships and employer strings from the review payload regardless), and align the Settings/Welcome/blueprint copy to the actual transmission.

3. **[MAJOR] `sendReturnContext` defaults to `true` — sharing is opt-out while all copy implies opt-in.**
   - Evidence: `clearfile/lib/ai/settings.dart:77` (`this.sendReturnContext = true`), `settings.dart:104-108` (`readBool(json, 'sendReturnContext', true)`); contrast `README.md:73` ("The AI cascade is **opt-in** … **no telemetry is sent**…") and `assistant.dart:34-36` ("figures the user **agreed to share**").
   - Why it matters: enabling the assistant is opt-in, but once enabled, return figures are attached by default under a switch whose subtitle implies a neutral default. Together with finding 2, the disclosed-data reality drifts from the marketing.
   - Recommended fix: default the switch to `false`, or keep `true` but state the default explicitly in the switch subtitle; pull the Stage 5 "in-app privacy disclosure tied to actual transmission behaviour" copy-fix forward into Stage 1 (it corrects current claims, not future hardening).

4. **[MAJOR] The GitHub release page — where all 8 binaries are side-loaded — carries no demo disclaimer and no non-advice language.**
   - Evidence: `.github/workflows/release.yml:289-297` — the release job uses `softprops/action-gh-release@v2` with only `generate_release_notes: true` (auto-generated commit list) and no `body:`; assets include the RE protocol doc and blueprint PDF; `harness/memory/STATE.md:10-13` confirms v1.0.0's release contents.
   - Why it matters: the release page is the landing surface for the binaries; a user who never opens the README sees zero "not IRS-authorized / cannot e-file / do not file a real return" language while the app computes real-looking refund numbers. For unsigned demo binaries the liability posture should be maximal.
   - Recommended fix: Stage 1 — add a `body:` to the release step (demonstration software; not IRS-authorized; cannot e-file; not tax or legal advice; binaries are unsigned) and edit the live v1.0.0 release description on GitHub to match.

5. **[MINOR] GPL-3.0 compliance is LICENSE-only; per-file headers absent and the nested `clearfile/README.md` is the untouched Flutter template.**
   - Evidence: `LICENSE` (canonical GPL-3.0, 35,149 bytes — verified) with no SPDX headers anywhere in `clearfile/lib/` or `src/`; `clearfile/README.md:1-17` — stock "A new Flutter project" text with no license or demo mention; `clearfile/pubspec.yaml:2` likewise template description.
   - Why it matters: GPL §5(c) permits source distribution with a top-level LICENSE (satisfied — and the release binaries' corresponding source is the public tagged commit), so this is hygiene rather than a violation; but headers are cheap protection against forks stripping attribution, and the nested README misinforms anyone landing in `clearfile/`.
   - Recommended fix: Stage 1's planned GPL headers; rewrite `clearfile/README.md` to reference the root README/LICENSE + demo disclaimer; also fix `README.md:23` — the `download/` row is stale since `df617e8`.

6. **[MINOR] `z-ai-web-dev-sdk@0.0.18` sits in `package.json` with zero usage and an unclear license.**
   - Evidence: `package.json:79`; no imports anywhere in `src/` (search for `z-ai-web-dev-sdk` in `src/`: none).
   - Why it matters: an unused dependency cannot taint the shipped standalone bundle, but a lockfile-pinned dependency of unverified license invites GPL-purity questions and is dead scaffolding.
   - Recommended fix: drop it in Stage 1.

7. **[MINOR] The Flutter Google transport puts the API key in the URL query string.**
   - Evidence: `clearfile/lib/ai/providers.dart:66` (`...generateContent?key=$apiKey`); the web prototype does it correctly via header (`src/lib/ai/ladder.ts:163`, `x-goog-api-key`).
   - Why it matters: keys in URLs are commonly captured in server/proxy/CDN logs — undercuts the "keys are sent only to the chosen provider" posture in spirit and is inconsistent across the two implementations.
   - Recommended fix: switch the Flutter call to the `x-goog-api-key` header (supported by the same endpoint).

8. **[MINOR] Web auto-fill can transmit SSN-bearing pasted text while the UI says "ClearFile never collects names, SSNs, or addresses."**
   - Evidence: `src/lib/ai/tasks.ts:84-89` — `extractPrompt` sends `raw.slice(0, 8000)` verbatim (a realistic W-2 paste includes SSN, name, address, EIN); contradicted copy at `src/components/clearfile/ai-ui.tsx:189-190` and `src/components/clearfile/settings.tsx:259`.
   - Why it matters: "collects" (storage) vs "transmits" (to the chosen provider) — the claim is over-broad for the auto-fill path.
   - Recommended fix: soften the copy ("ClearFile does not *store* names or SSNs; anything you paste into auto-fill is transmitted to your chosen provider") or add a pre-send notice/redaction option.

9. **[MINOR] The backup script's `git add -A` denylist misses `upload/`, and the secret guard covers only token patterns.**
   - Evidence: `scripts/sandbox_backup.sh:33` (`git_add -A`), `:41-48` (guard matches only `github_pat_`, `sk-…`, `AIza…`); `.gitignore` "sandbox backup scope" block ignores `.env`, `db/`, `.zscripts/`, `Caddyfile`, `tests/`, `examples/`, `mini-services/`, `tool-results/`, `download/`, `tools/` — but a top-level `upload/` directory **exists on disk and is not ignored** (currently empty, verified).
   - Why it matters: the event-driven backup stages everything not ignored and pushes to a **public** repo. A future session that drops a stray file in `upload/` (a platform drop-zone) — or a scratch file with pasted `.tax` hex dumps or PII anywhere outside the ignored paths — would be auto-published, and the token-pattern guard would not catch it. This is the mechanism by which the next nitro_nissi-class incident happens.
   - Recommended fix: Stage 1 — add `/upload/` to the ignore block; better, invert to an **allowlist** of top-level paths (`clearfile/ src/ docs/ harness/ scripts/ prisma/ public/ .github/ blueprint-assets/` + root files) in the backup script, or extend the guard with binary/hex-blob heuristics.

10. **[NOTE] RE protocol §2 is legally sound; two guardrails are missing before Stage 2 builds tooling.**
    - Evidence: `docs/reverse-engineering-protocol.md:26-66` — the EULA/Sega/Sony/§1201(f) framing, the research-vs-distribution line, and the no-keys/IVs/decryptors rule are correctly stated; §6:180-181 already bars key material, copyrighted form text, and bulk proprietary content; the key-bearing write-up is described and **linked**, never reproduced (`:15`, `:166-169`). I verified the repo honors it across history: no AES key/IV values, no decryptor code, anywhere.
    - Why it matters (gaps): §3 Phase 3 (differential analysis) never says the file pairs must be *owner-authored*; and there is no rule for what a `docs/formats/*.md` spec may quote from a proprietary binary (verbatim strings/screenshots are expression; offsets/dtypes are not).
    - Recommended fix (before Stage 2): append to the protocol — (i) differential analysis runs only on file pairs the owner authored in their own licensed install; (ii) decrypted content is never committed or published; (iii) spec field tables may record the *existence* of per-year crypto constants, never their values; (iv) no verbatim strings longer than a few identifier bytes and no screenshots from proprietary binaries; (v) a pre-commit checklist for RE findings. Describing-and-linking a public write-up is materially different from providing the means; keep it that way.

11. **[NOTE] Clean-room expression audit passes — the §102(b)/Merger/scènes-à-faire line is honored.**
    - Evidence: interview copy is original throughout (`clearfile/lib/ui/steps/*.dart`; `review_rules.dart:38-80`); filing-status explanations are original phrasings of statutory criteria (`filing_status.dart:5-28`) and the "Form 1040-style summary" labels derive from IRS government-edict forms (`results.dart:229`); engine parameters are facts with cited sources (`tax_year.dart:15-29`); no marketing-tone lift anywhere. "TurboTax-class" (`README.md:6`) and `docs/` references to TurboTax are descriptive nominative use, not affiliation claims; branding carries no Intuit marks (`android:label="clearfile"`, `clearfile/web/manifest.json`, `src/app/layout.tsx:21`).
    - Recommended fix: none; keep TXF record codes as facts (`src/lib/files/txf.ts:5-13`).

12. **[NOTE] Two wording/accuracy tensions.**
    - `src/app/layout.tsx:18` titles the web app "Clean-Room Tax **Filing** Assistant (Prototype)" — sits awkwardly with "not IRS e-file software. Do not use it to file a real return" (`steps.tsx:95`, `shell.tsx:186`); consider "Tax Return Study Prototype".
    - Release Android APKs lack the `INTERNET` permission (only debug/profile manifests declare it) and macOS `Release.entitlements` has no network-client entitlement — the shipped release binaries cannot run the advertised AI cascade at all. Primarily an engineering defect (ADV-ENG's seat), but it also makes the README's AI-feature claims inaccurate *as shipped*; fix alongside the release-page work.

## Roadmap assessment

- **Stage 1 (Hardening & trust):** correctly sequenced; from the compliance seat the history decision is the top item and must start with **nitro_nissi provenance verification** (finding 1), and any rewrite must preserve v1.0.0's corresponding source (GPL §6). Add to scope: release-page disclaimer (finding 4), `upload/` ignore / backup allowlist (finding 9), GPL headers + nested README fix + stale `download/` row (finding 5), drop `z-ai-web-dev-sdk` (finding 6), and the privacy-copy corrections of findings 2–3 (do not defer those to Stage 5).
- **Stage 2 (Format-study):** right scope — Phases 1–3 only, no binaries, spec-first. But write the finding-10 guardrails into `docs/reverse-engineering-protocol.md` **before** the tooling exists, since tools make accidental publication mechanical; the roadmap's note that "ADV-LEGAL carries extra weight at this gate" is correct and should be retained.
- **Stage 3 (Bridges):** lowest legal risk, highest value. TXF record codes are facts of a published interchange format; IRS-pinned parity tests are the best possible trust artifact. No conditions.
- **Stage 4 (Platform reach):** a GitHub Pages deploy puts the "filing-adjacent" UI on a public origin — ensure the welcome disclaimer is prominent (it is, `welcome.dart:92-99`), and confirm the copy fixes from Stage 1 land before the hosted build goes live. Unsigned `.aab`/AppImage posture should be stated on whatever page hosts the download.
- **Stage 5 (AI hardening):** the in-app privacy disclosure item is the right idea at the wrong time — the disclosure-vs-code mismatch exists today (findings 2, 3, 8) and is cheap to fix now; leave only the *forward-looking* hardening (prompt-injection tests, fixture cascade e2e) in Stage 5.
