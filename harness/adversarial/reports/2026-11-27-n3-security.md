# ADV-SEC — N3 delta-scoped gate (2026-11-27, Task N3-GATE-SEC)

Reviewer: ADV-SEC (secrets/CI-CD/supply chain/untrusted-input surfaces + guard
joins + this gate's riding hardening items). The N3 proposal under review: the
orchestrator's consolidation — the separate-root `core-ffi/` crate (flat C ABI
over the core, cbindgen header, thin android-cfg JNI shim, cdylib), the
`apps/android/` Gradle app (KMP-shaped, one target, Android Views, SAF open,
MD3-from-seed via the palette FFI), verification via host FFI tests + a CI
android job, and my lane's riding items (the duplicate-scan bound-or-record
framing "closure before FFI wiring"; the R2 file-size pre-check). Read first,
as instructed: ROADMAP 547–670, ADR-017, STATE "Immediately next", the
CONSENSUS N2-exit + discharge records, my N2-exit report, ROLES.md. The
sibling N3 reports (LEGAL/ENG/PROD) were neither read nor written.

The proposal's shape is sound and — measured live today — lighter than
assumed: the ubuntu-latest (24.04) runner image preinstalls the Android SDK
**and** the NDK (verified from the image readme, below), so the CI android
job needs **no** new SDK/NDK download class, only fail-closed version
assertions. Two measured facts overturn premises in the records: free disk is
**1.7 GB**, not the ~5–6 GB class the STATE/backup records carry (a local
SDK+NDK fetch is infeasible; CI-primary is forced, not merely chosen), and
the sandbox's Java is a **JRE only** (`javac` absent, no gradle/kotlinc on
PATH) — so the "JVM unit tests loading the host .so" run **CI-only** unless a
pinned JDK fetch is funded; the FFI seam itself is provable locally with
cargo alone (Rust-side boundary tests call the `extern "C"` surface directly —
no JVM needed). The real work of this gate is pinning the boundary discipline
(panic containment, ownership, JNI marshaling), landing the riding hardenings
BEFORE the wiring, and pre-empting the one genuine supply-chain collision I
found: the Gradle wrapper jar vs. the repo's own-authored-only blob policy.

**VERDICT: PROCEED-WITH-CONDITIONS (11)**

## Conditions

1. **Panic containment at every export — no panic ever crosses the boundary.**
   Every `extern "C"` function in core-ffi wraps its whole body in ONE shared
   `catch_unwind` (AssertUnwindSafe) helper mapping a panic to the error
   status + the thread-local last-error string in the core's wording family;
   never rely on the abort-on-unwind-out-of-`extern "C"` semantics. A
   panic-injection test (a test/feature-gated entry that panics, wrapped by
   the same helper) proves the mapping once. Checkable:
   `rg -n 'catch_unwind' core-ffi/src` (one shared wrapper used by every
   export) and the panic-injection test green in
   `cargo test --locked --manifest-path core-ffi/Cargo.toml`.
2. **The ABI contract is pinned IN the header.** Strings/bytes only — no
   `#[repr(C)]` struct mirrors of core types (the envelope as the payload
   boundary); inputs are `(const pointer, explicit length)` pairs (NUL-safe),
   UTF-8-validated with named errors; NO path parameters anywhere (the
   platform owns file acquisition — SAF on Android; the cdylib never touches
   the filesystem). Exactly TWO documented return classes: owned buffers
   freed ONLY via the single `clearfile_free` (NULL-safe; freeing via libc
   directly is documented UB), and `clearfile_last_error` returning a
   borrowed thread-local pointer that is NEVER freed (valid until the next
   call on that thread). Checkable: read `core-ffi/clearfile.h` — zero struct
   bodies with fields, zero path params, the two lifetime classes documented
   as comments; `rg -n 'fs::' core-ffi/src` → no filesystem access.
3. **The JNI shim marshals payloads as `jbyteArray`, never `jstring`.**
   JNI's `GetStringUTFChars`/`NewStringUTF` speak Modified UTF-8 (CESU-8
   surrogates, embedded-NUL encoding) — a real corruption class for envelope
   JSON with non-ASCII taxpayer names; byte arrays end-to-end avoid it
   entirely (error strings included, or the last-error family is proven
   ASCII). The shim must ALSO compile on the HOST so the JVM test lane can
   `System.load` the host-built .so — reconcile the proposal's
   `cfg(target_os="android")` (the shim uses only the JNIEnv ABI, no Android
   APIs: gate on `any(target_os="android", feature="host-jni-tests")` or drop
   the gate); the flat C ABI stays the single audit surface — the shim is a
   thin translation with no logic of its own. Checkable: a host
   `cargo build` produces Java_*-exporting symbols; the JVM test loads the
   host .so and passes.
4. **The battery runs THROUGH the boundary.** core-ffi's test module calls
   every C function over (a) all 17 golden fixtures asserting parity with
   direct core calls, (b) the malformed-ZIP crash battery classes and the
   malformed envelope/JSON classes (each yields the named error status +
   last-error string equal to the core's message; the test binary never
   aborts), and (c) the two cap batteries (the 10,001-member refusal; the
   256 MiB STORE stop-note) through the boundary. Checkable: the test files
   exist under core-ffi/tests and are green in
   `cargo test --locked --manifest-path core-ffi/Cargo.toml`.
5. **The duplicate-scan amplification is BOUNDED in session 1, BEFORE the FFI
   wiring — record-only is NOT acceptable** absent a recorded owner ruling
   (my N2-exit standing framing: closure before any FFI wiring, and N3 IS
   the wiring; the exit-gate record rides this as the ENG item). Either
   shape: (a) a cumulative duplicate-key comparison budget tripping a new
   named error in the existing wording family (the TooManyMembers
   offset/count style), or (b) an order-preserving index (e.g. a
   key→position map engaged past a size threshold) preserving the pinned
   first-position/last-value-wins duplicate semantics. Either way the battery
   extension lands: the crafted ~10,000 long-common-prefix duplicate-key case
   (the measured tens-of-seconds class) now completes sub-second or errors
   namedly, plus a just-under-twin that still parses. Intra-session
   checkpoint: core tests green including the new battery BEFORE the first
   core-ffi commit. Checkable: the new tests in core (e.g.
   `rg -n 'duplicate' core/src/json.rs core/tests/`), and `git log` shows the
   core-hardening commit preceding the first core-ffi commit.
6. **The file-size pre-check (R2) lands with N3 at every entry surface.**
   Refuse >512 MiB pre-read with a named message in the core's wording
   family: at birth in the apps/android pipeline AND as the apps/linux
   retrofit (the R2 discharge — edit `apps/linux`'s `load_and_compute`
   read path), PLUS core-ffi rejects any input payload >512 MiB at the
   boundary (defense-in-depth: the C boundary is the permanent surface
   N4/N5/N6 consume). The core stays pure (no fs in core; its byte-slice
   caps are unchanged). 512 MiB is the right uniform bound (generous against
   KB-scale real envelopes, bounded against RAM); an Android-local tighter
   bound with the same message family is allowed if recorded. Checkable:
   the named refusal message greps in all three places
   (`rg -n <message> apps/ core-ffi/src`) + one battery test per place.
7. **core-ffi's supply chain follows the apps/linux precedent exactly.**
   `core-ffi/deny.toml` from the FIRST commit — core-ffi is the crate
   carrying the first BUILD-time external dependency (cbindgen), so it owns
   the closed allow-list (the N2-recorded 11-id GPL-3.0-compatible family +
   the wildcard disposition for the clearfile-core path dep), sources
   crates.io-only, yanked/wildcards deny, covering build-deps. cbindgen
   pinned to an EXACT version; every build `--locked`. The generated
   `core-ffi/clearfile.h` is a COMMITTED tracked artifact (it is the N4/N5
   contract) with a CI freshness check: the pinned cbindgen regenerates to a
   temp file and `diff` against the tracked header fails on drift.
   Checkable: files exist; the CI step; a first green run.
8. **The Gradle supply chain — no committed wrapper jar (blob-policy
   collision pre-empted).** `scripts/check_binary_blobs.py` allows ONLY
   own-authored binaries (verified: "a binary that is not own-authored is
   never added, it is removed"), so `gradle/wrapper/gradle-wrapper.jar` MUST
   NOT be committed (no policy exception for Gradle's binary). Two
   acceptable shapes: (a) CI-primary — the runner's preinstalled Gradle with
   a fail-closed version assertion (the readme I fetched live lists Gradle
   9.9.1; assert `gradle --version` matches the pin, refuse otherwise), or
   (b) a tracked sha256-pinned gradle-distribution fetcher in the
   fetch_rust_toolchain class if reproducible local builds are demanded —
   record the chosen lane. Additionally: gradle dependency LOCKING enabled
   with the lockfile(s) committed (the --locked analogue), repositories
   google()/mavenCentral() only, exact-pinned AGP/Kotlin plugin versions,
   and a minimal dependency set (androidx core/appcompat/material class
   only; no network/AI libraries). Checkable: no `gradle/wrapper/` dir in
   the tree; `rg -n 'dependencyLocking' apps/android` + the committed
   lockfile; the CI gradle-version assertion.
9. **The CI android job's posture (hygiene.yml's android lane):** permissions
   contents:read at workflow AND job level; SHA-pinned actions ONLY — any
   NEW action's tag↔SHA resolved live and recorded (the discharged SEC-riding
   precedent); a fail-closed environment guard FIRST (parse `java -version`
   and `command -v javac` — the runner's JDK listing was NOT verified from
   this sandbox; assert the ANDROID_HOME SDK and the exact NDK pin (the

   assert its path/version, never trust the default env); the rustc guard

   cross-build); `timeout-minutes`; no secrets.*; NO artifact uploads

   run on the tip.

## Risks register

1. **Runner-image toolchain drift** (ubuntu-latest remaps; preinstalled
   SDK/NDK/Gradle/JDK versions change silently — the readme's platform list
   already includes betas). The fail-closed assertions (conditions 8/9) turn
   drift into a red build rather than a silent toolchain swap; residual: the
   job reds until re-pinned. Accepted.
2. **Unverified runner facts.** I verified the image readme's Android rows
   and Gradle 9.9.1 live, but NOT its JDK rows nor any actual job (no android
   job exists yet); cbindgen's current version/license could NOT be verified
   live (the crates.io API probe returned nothing parseable from this
   sandbox). Both covered mechanically: the fail-closed java/javac guard and
   the landing deny.toml over the actual lockfile + the exact pin.
3. **The no-wrapper choice ties local reproducibility to the runner image**
   (measured locally: JRE-only Java, no gradle/kotlinc, 1.7 GB free — the
   app cannot be built in this sandbox at all). Acceptable for a demo that
   ships nothing; revisit at the GA lane with a recorded decision.
4. **JNI-surface creep** — the shim accreting logic until it becomes a
   second ABI. The header stays the one audit surface; the exit gates
   re-assert the thin-shim shape.
5. **The duplicate-scan window until the bound lands** — session-1 ordering
   (condition 5's checkpoint) is the control; within-session only.
6. **512 MiB on Android RAM ceilings** — a 512 MiB read can still ANR/OOM a
   low-RAM device; the uniform bound is accepted for the demo, with the
   recorded tighter-bound option (condition 6).
