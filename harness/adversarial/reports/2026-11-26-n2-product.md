## Mandate rulings (the six probes)

**(1) Is the consolidation honest — gate's own right, or does it owe an
owner surfacing? RULING: the gate's own right, with recording duties.**
ADR-017's Linux-toolkits row (DECISIONS 513) ends: "The two-tier split
may consolidate to one toolkit **at the N2 entry gate** if
single-maintainer reality demands it **(revisitable, recorded)**." The
ADR text itself delegates the consolidation to THIS gate, conditioned
only on the demand being real. That is categorically different from
the owner-decision adjacencies that owed surfacings: the
Stages-4/5/6 after-the-fact sequencing was valid only "under an
explicit owner directive, never by default," and the PAT use classes
were surfaced for ratification because they exceeded the token's
recorded profile — both were UN-pre-authorized deviations. This one is
an in-ADR delegation with its conditions named. **No owner ruling is
owed.** The demand is genuine and now double-measured (the proposal's
measurement + mine: no `libgtk-3-dev`, no root, no pkg-config entry —
the older tier is undevelopable in the single maintainer's only
execution lane, making it a CI-only blind-maintained second UI). The
"(revisitable, recorded)" parenthetical carries the duties: record the
demand's evidence, the forfeit, and the revisitability (Condition 1).
Because the two-tier split was itself "settled by the owner's literal
two-tier assignment" (ADR-017 context, 558–561), a one-line owner-FYI
(not a ruling request) is best practice and matches the D30 standing-
surfacings shape (Advisory 1). The forfeit's interim product impact is
near zero: the Flutter Linux app (itself GTK3) remains the shipped
Linux product until the native GA, so old-distro users lose nothing
during the transition — the eventual native old-distro coverage becomes
a GA-gate build-target question (glibc baseline), which the record
should name (Condition 1d, Risk 6).

**(2) Sequencing — is N2-first still right, and should N4 jump N3?
RULING: N2 next is right; keep N3 before N4; pre-position, don't
re-order.** The per-OS order after N1 is "re-settable at the epilogue's
own gates without reopening the ADR-017 settlement" (ROADMAP 632–634),
so this gate COULD re-order — but there is no measured demand to: N3's
sandbox gap (no Android SDK/NDK — measured, point 4 above) is
user-space-mitigable exactly like the Rust toolchain was (a tracked
sha256-pinned fetcher; `sdkmanager` needs no root; GitHub's ubuntu
runners ship the Android SDK at `/usr/local/lib/android/sdk`), while
N4's in-sandbox cross-build is no better off (no mingw, no root to
install it — a portable toolchain or CI windows runners mitigate).
Re-ordering on unproven infeasibility would be the D32-shaped
pre-emptive mistake; the settlement's own pattern is that a stage's
gate rules its feasibility live with measurements (ADR-017 recorded
macOS's sandbox infeasibility IN the ADR with its CI-runner
mitigation — N3's gate owes the same live ruling). N2 itself is the
right next stage by feasibility as well as record: Slint builds here
(measured) and the local Xvfb+libxkbcommon stack makes N2 the only
fully in-sandbox-developable UI stage. Condition 6 carries the
pre-positioning.

**(3) The working-app bar. RULING: the argv-envelope + MD3 window +
--headless slice MEETS the stage bar only as a LABELED viewer demo —
the honesty surfaces are not optional.** ADR-017's epilogue-sequence
row (509): "Each stage lands a working app before the next starts."
N2 is the first stage that sentence literally binds (N1 landed the
core, fixture-verified, with its own exit checklist instead). The demo
shape (argv envelope → core import/compute → a themed window + a
headless text mode) is defensible for a re-platforming stage — it
proves the stack, the theme, and the core wiring — PROVIDED the app
says what it is: the demo disclaimer (demonstration software / do not
file — mirroring README 292–301), a prototype/About note naming the
argv-only input, no editing, no picker, and the roadmap to them; and a
README row stating the Flutter app remains the shipped Linux product
until the native GA. Argv-only IS defensible for a desktop app at
demonstration standards when labeled — and there is a hard constraint
that makes it MORE defensible: the standard Rust file-dialog crate
(`rfd`) uses GTK on Linux — the exact build dependency being forfeited
(Advisory 3). Condition 4 makes the bar checkable via an N2 exit

**(4) v2.0.0 discipline. VERIFIED HONORED.** ADR-017's v2.0.0 row: the

## Risks register

- **Box slip (one-session optimism)** — the palette port + corpus +
  first-ever Rust UI + CI in one lane is N1-two-session mass; the
  N1-session-2 parallel-lane timeout class is on record. Mitigation:
  Condition 3.
- **Disk exhaustion mid-session** — measured 1.5 GB free vs ~1.3 GB
  for a debug-stripped Slint build + the Dart reference runtime; the
  naive full-SDK plan does not fit. Mitigation: Condition 3(iii).
- **Integer-parity boundary case** — HCT/CAM16 transcendental math
  (Dart libm vs Rust libm last-ulp differences) rounding across an
  8-bit channel boundary in some seed; a late corpus failure would
  tempt a silent tolerance. Mitigation: Condition 5 (pre-declared
  semantics).
- **Indefinite slip parking (Stage-2 exit)** — third consecutive cycle
  chained through an owner-uncommitted T3 lane. Mitigation: Condition
  7(a) keeping the options surfaced; the pattern's proof would be a
  fourth cycle without a ruling.
- **Hostile-input freeze surfaced to GUI users** — R1/R2 become
  user-reachable via argv before the FFI hardening lane. Mitigation:
  Condition 7(c).
- **Old-distro native coverage gap after GA** — the forfeited gtk3
  tier was the old-distros story; the interim is covered by the
  still-shipped Flutter GTK3 app, but the GA gate owes a glibc/distro
  baseline decision or the gap returns at retirement. Mitigation:
  Condition 1(d).
