## Conditions

1. **The N1-exit registered parser-hardening risks land at N2 in substance and must be discharged or explicitly re-deadlined in N2's session**: the O(n²) JSON object-key insertion (`core/src/json.rs::parse_object`) and the ZIP STORE amplification (`core/src/tax_inspect.rs::read_zip_directory`) were registered "before the first FFI-wiring session", but N2 is the first session that feeds user-opened files to these parsers inside a shipped binary — the direct Rust link dodges the letter of the trigger while arming its substance (the N1-exit measurements stand: 80k keys → 26.8 s CPU; 385 KB crafted ZIP → >1 GB allocs). **Verification:** the N2 session either lands both hardenings (a member-count/linearity bound in `parse_object` + a cumulative extracted-bytes cap in `read_zip_directory`, each with a battery extension pinning it) or DEBT.md gains an explicit re-deadline note naming direct linking as the rationale — absent both, the session is out of posture.
2. **The cargo-deny posture must be picked, recorded, and fail-closed in apps/linux's FIRST commit, from only two acceptable options:** (a) EmbarkStudios `cargo-deny-action` SHA-pinned per D10 — acceptable because it is the same trust class as the already-accepted SHA-pinned `gitleaks-action` (a third-party action that also downloads a third-party binary at runtime), or (b) `cargo install cargo-deny --locked --version <pinned>` — crates.io-origin tooling build, no new action, costs CI minutes; a VENDORED BINARY is forbidden by the existing binary-blob policy (`scripts/check_binary_blobs.py`: "a binary that is not own-authored is never added, it is removed"), and a plain fail-closed script ALONE is insufficient (Cargo.lock carries no license metadata — verified: license fields live only in registry manifests, not the lockfile). **Verification:** the first apps/linux commit contains the picked mechanism, its rationale in the commit note, and a tracked `deny.toml` (licenses: GPL-3.0-only allowed; sources: crates.io-only — the audited tree is 100% registry-sourced; bans + advisories configured).
3. **The audited tree must be the built tree:** apps/linux's Cargo.toml must bound slint to the audited series (`slint = "1.19"` — the probe's `"1.13"` caret resolved to 1.19.1 and would silently admit unaudited future minors), and CI must build/test `--locked` with `apps/linux/Cargo.lock` committed. **Verification:** `grep -n 'slint' apps/linux/Cargo.toml` shows the 1.19 bound; the new CI steps carry `--locked`; `git ls-files apps/linux/Cargo.lock` is tracked.

## Risks register

1. **The 552-crate crates.io tree is the repo's largest external-code import** (larger than the npm dev tree, comparable in class to the accepted production npm tree), built on EVERY push once the CI lane lands. Mitigations present: 100% registry-sourced (zero git/path-foreign deps — verified), full checksum coverage in the lock, `--locked` builds (condition 3), cargo-deny bans/licenses/advisories (condition 2). Residual: crates.io-typo/squatting risk inside slint's tree is inherited wholesale — accepted as a class by the roadmap's consolidation grant, but it must be *recorded* as accepted.
2. **apt-get arrives on the push+weekly lane** (libxkbcommon-x11 + Xvfb for the window smoke). Ubuntu-archive trust already has an accepted precedent (`release.yml:239-240` sudo-installs libgtk-3-dev et al.), but only on the tag/dispatch lane; the hygiene lane is scheduled unattended. Blast radius is bounded (ephemeral runner, `contents: read`, no secrets) — accept and record, do not silently widen further (no third-party apt repos).
3. **Xvfb in CI**: a display server process on the runner — standard practice, ephemeral, read-only job scope; the window smoke must assert observable behavior (the probe's "app-window-created-ok" pattern), not just exit 0.
4. **The ADR-017 variant boundary ("no shipped artifact depends on the core") is one edit away from ending**: wiring apps/linux into `release.yml` ends the variant; `harness_check`'s release.yml guard mechanically catches it today (`core/|clearfile-core|cargo` count = 0). Keep the N2 app CI in `hygiene.yml`; a release.yml wiring requires its own recorded variant-change decision, not a rider on this delta.
5. **Toolchain skew**: the sandbox builds with the pinned 1.100.0 fetched toolchain; CI builds with runner-image rustup rust (the recorded posture — no toolchain actions). A 552-crate tree raises the odds of version-sensitive build breakage; the new job should echo `rustc --version` (existing precedent) and the minimum rustc requirement should be recorded if the tree needs it.
6. **skia-safe/skia-bindings sit in the lock but never compile on Linux** (Apple/iOS target-gated — verified); BSD-3-Clause, license-clean, but the N5 (macOS) session WILL pull them into a build — recorded here so that session's audit starts warned.

## Advisories

1. Enable cargo-deny's `[advisories]` vulnerability check with a recorded severity threshold, matching the npm-audit-at-critical precedent (hygiene.yml's `npm audit --omit=dev --audit-level=critical`); the RustSec advisory-DB fetch in CI is the same network-trust class as npm audit's registry fetch.
2. The app crate should declare `publish = false` (core precedent) — the artifact posture stays non-published until a release decision exists.
3. `--headless`/argv parsing is an untrusted-input surface: keep it a strict hand-rolled parser (unknown flags refused), the envelope path its ONLY file input, and never shell out / open URLs from input; the core parsers carry the input-validation burden (battery-hardened), so the app layer should stay a thin pass-through.
4. The core's zero-dependency assertion (hygiene.yml) is scoped to `core/Cargo.lock`/`core/Cargo.toml` and stays green under the separate-crate topology (verified: no workspace, path dependency recorded only in the app's lock) — do not weaken it when the cargo-deny step lands alongside.
