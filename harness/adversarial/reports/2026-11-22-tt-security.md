## Findings

1. **[MAJOR] The key-material hygiene backstop does not cover the sanctioned shape, and its landing is not sequenced against the TT program.** A 16-byte AES key serialized as 32 contiguous hex chars passes the backup guard today (`{64}`-only, sandbox_backup.sh:92) — in any note, spec, test, or doc. The planned widening (ROADMAP:269, LEGAL-1: ≥32-hex on RE-adjacent paths + UUID/known-hash allow-list) is bound to the *first Stage-2 tooling commit*, but the owner's active directive is the TT program; T2–T4 can reach the quarantined key module with Stage-2 session 1 still "standing" (PROJECT_MEMORY:147). The boundary "key values in exactly ONE bridge module" (ADR-020:756–760) is policy, not mechanics, until the widened guard is on the critical path *ahead* of the key module.

2. **[MINOR] The commit-message channel is unguarded.** ADR-020 forbids key values in commit messages; the only automated publish path commits the operator-supplied NOTE verbatim (sandbox_backup.sh:116) with no token/hex scan. The guard checks the staged tree, not the message it creates.

3. **[MINOR] Corpus integrity verification is manual.** fetch_tt_corpus.sh verifies byte-size only; sha256s are printed for human comparison against the manifest, not mechanically enforced. This corpus is the clean-room derivation source for material that will ship in the product, and `tools/` is wiped by every sandbox recycle — re-fetch is a recurring event, each one an unverified ~1.4 GB acquisition.

4. **[NOTE] Hex-run heuristics are representation-limited.** A `Uint8List.fromList([0x48, 0x12, …])` byte-array literal evades any contiguous-hex guard. The widened guard is necessary but not sufficient for the single-module confinement; a representation-agnostic assertion is needed on the sanctioned side.

5. **[NOTE] Widened-guard false-positive inventory (measured, must be in the allow-list design):** workflow SHA pins (40-hex, 25+ hits in `.github/workflows/`), `clearfile/.metadata` revisions, `blueprint-assets/body.pdf` (binary — `-I`-skipped), lockfiles, UUID-shaped 32-hex runs. Without enumerating these, a repo-wide ≥32-hex guard reds the backup/CI on day one and invites hasty loosening.

6. **[NOTE] Positive verifications.** Delta hygiene is clean: no app code, no tokens anywhere in history, no hex beyond the manifest, CI surfaces unchanged, corpus fully gitignored/untracked, gitleaks full-history in CI, no RE tooling in release.yml. ADR-020's ordering (acceptance recorded before any decryptor exists — verified none exists at tip) is exactly what ADR-019 demanded; the protocol amendments are dated, scoped, and leave §7.2/§7.4 intact. The `password = authorization` frame with refusal tests and wrong-password-clean-failure is already binding text (ADR-020:752–755).

7. **[NOTE] T4's threat model is recorded as boundary conditions but not yet as merge conditions.** The recorded security contract (ROADMAP:231–246) is written for Stage-2 *analysis* tooling (write-free); the bridge is a shipping read/edit/save parser of untrusted input — its contract (crash battery, resource caps, no-network, timing-leak-free password failure, fixture discipline) needs explicit spelling-out at the T4 merge, and bridge tests must not commit ciphertext-under-shipped-keys as fixtures.

## Verdict

**PROCEED-WITH-CONDITIONS.** The repository state at this gate is sound — delta clean, containment verified, no secrets in tree or history, CI/release isolation intact, ADR-020 recorded in the correct order with a coherent risk register. Nothing advancing T2 would be reckless: T2 is read-only study of gitignored corpus producing function-fact notes. The conditions below make the ADR-020 boundary mechanically real before the point where it must hold (the T4 key module), and pin the shipped-decryptor threat model.

1. **(Before the T4 key module exists; ideally with T2's first tracked note commit)** Land the LEGAL-1 hex-guard widening in `scripts/sandbox_backup.sh`: ≥32-hex on RE-adjacent paths (`docs/`, `clearfile/`, `src/`, `scripts/`, `fixtures/`, `harness/`) with a measured allow-list (corpus-manifest.md, `.github/workflows/*.yml` SHA pins, `clearfile/.metadata`, lockfile classes, UUID shapes — finding 5's inventory). Checkable: the widening commit precedes the key-module commit in `git log --oneline`; a canary file containing a 32-hex run outside allow-listed paths makes the backup exit 2.

2. **(Same commit that introduces the T4 quarantined key module, at latest)** A representation-agnostic single-provenance assertion: a CI step or harness_check pattern that extracts the quarantined module's key constants and fails if any serialization of them — contiguous hex, byte-array literal, or base64 — appears in any other tracked file; the guard's allow-list grows by exactly that one module path. Checkable: negative canary (inject the key hex into a scratch test file) reds the assertion.

3. **(Before T4 merge)** Scan the backup NOTE for `TOKEN_PATTERNS` and ≥32-hex before committing (exit 2 on hit), closing the commit-message channel. Checkable: run with a NOTE containing a 32-hex string → refused.

4. **(At T2 start)** Mechanical corpus verification: `fetch_tt_corpus.sh` greps the expected sha256 from `corpus-manifest.md` and refuses on mismatch (exit 1), instead of printing for human comparison. Checkable: a one-byte-corrupted copy of a target fails the fetcher.

5. **(T4 merge gate — the shipped decryptor's threat model; each item test-checked, per the ENG-1 template in `clearfile/lib/io/tax_inspect.dart`)** (a) malformed-input crash battery: bounds-checked slices on every length-prefixed read, entry cap, never-throws "reports what it could not establish" contract; (b) resource bounds: file-size, entry-count, and nesting/decompression-depth caps, **each with a refusal-on-oversize test**; (c) password gate: wrong password = one uniform clean-failure message, no key-derivation-vs-parse error split, no timing oracle (identical work and padding on all failure paths), no password/key/derived material in any log path, no network calls in the bridge module (no `http` import there; the AI cascade stays a separate opt-in surface); (d) test fixtures are generated at runtime via the quarantined module — no committed ciphertext-under-shipped-key fixtures under `fixtures/re/`; (e) README/SECURITY ship-time provenance disclosure per ADR-020. Checkable by reading the bridge code and tests; execution wiring verified present (hygiene suites + release `flutter-test` needs-gated for all five platform builds).

6. **(T3 specs)** The `docs/formats/*.md` provenance lint (no hex runs ≥32) must cover `docs/re-research/` notes too, since T2/T3 notes are the likeliest accidental leak surface for derived constants; specs stay by-existence per the §7.3 amendment. Checkable: a canary note with a 32-hex run fails the lint.

The owner's acceptance governs legal risk; conditions 1–6 govern the mechanical and security surfaces this panel owns. None of them narrows the acceptance — they make its boundary conditions executable, which is what "recorded, not aspirational" requires.
