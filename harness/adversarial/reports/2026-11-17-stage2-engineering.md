## Findings

1. **ENG-1 [MAJOR] — the shipped Dart `.tax` inspector crashes on malformed input, violating its own contract.** `clearfile/lib/io/tax_inspect.dart:85-86` documents "Never throws on malformed input — the analysis reports what it could and could not establish", and `_readZipDirectory` checks only `ptr + 46 > bytes.length` (line 249) before `bytes.sublist(ptr + 46, ptr + 46 + nameLen)` (line 261) — a central-directory entry whose name field runs past EOF throws `RangeError` (reproduced above). Call sites don't catch: `app_state.dart:137` returns it bare; `welcome.dart:306` (`_inspectTax`) shows the dialog with no try/catch — a user opening a corrupt/crafted `.tax` file crashes the app. The web twin handles the same bytes gracefully (`taxfile.ts:221`, slice clamps) — exactly the robustness divergence parity exists to prevent. This is the untrusted-input hardening class Stage 3 claimed to close. **Fix:** bounds-check `ptr + 46 + nameLen <= bytes.length` (note + break, mirroring the existing truncated-entry branch) and add my crafted file as a regression test in `tax_inspect_test.dart` (the suite currently pins a missing-EOCD truncation, line 159-169, but not this one).
2. **ENG-2 [MINOR] — one of the three advertised TXF caps is untested.** `txf_import.dart:68-70,116-119` define 5 MB / 10,000 records / 4096-char caps; `txf_import_test.dart` pins only the 5 MB cap (line 228) and the 4097-char line (line 233). The 10k-record cap (`records.length > _maxRecords`) has no test, so the ROADMAP claim "5 MB/10k-record/4096-char hardening caps — 11 tests" overstates coverage. **Fix:** one test emitting 10,001 `N460` records expecting the refusal.
3. **ENG-3 [MINOR] — the parity contract has a survivingSpouse hole.** No golden fixture exercises QSS (`rg survivingSpouse fixtures/tax/` → 0); the only Dart pin is an internal equivalence test (`calculator_test.dart:224-230`, QSS vs MFJ at one input — blind to both-wrong-together drift); the TS engine's QSS path (`config.ts:182-185`) is pinned by nothing at all. Both engines' QSS tables currently match (I diffed them), but a silent future divergence would pass every gate. **Fix:** one QSS fixture (pins standard deduction 31,500, CTC phase-out 400k, QDI caps 96,700/600,050, NIIT 250k — all currently unpinned per-status values) consumed by all three runners.
4. **ENG-4 [MINOR] — the v1→v2 migration is triple-implemented with fragment-level pinning and edge drift.** The same conservative mapping lives in `cfr.ts:73`, `store.ts:140`, and `return_format.dart:172`. Drift already present: Dart clamps migrated child counts at 100 (`return_format.dart:214-215`) while web does not (`cfr.ts:100-101`); warning "parity" is pinned only by `contains` fragments (`return_format_test.dart:152-160`, `txf_taxfile_test.mjs:342-345`), never by full warning-list equality; and `store.ts:155` reads the v1 *store* shape's `w2s.federalWithheld` while both file readers read the v1 *file* shape's `w2s.withholding` (`cfr.ts:176`) — legitimate (different v1 vintages) but documented nowhere. **Fix:** lift the identical v1 sample into a shared fixture file, assert exact warning lists in both suites, and document the store-vs-file W-2 shape difference in `docs/return-format.md` §3.
5. **ENG-5 [MINOR] — the durable SDK fetcher aborts before its own smoke test; quirk unrecorded.** `fetch_flutter_sdk.sh:13` (`set -euo pipefail`) + `tar -xJf` (line 64) means any nonzero tar exit — including the benign trailing directory-status restore failure this snapshot FS now exhibits — kills the script before `flutter --version` (line 65), so the authoritative smoke test never runs and the "OK" line never prints. Nothing in STATE quirks 1-19 records this. **Fix:** capture tar's exit, always run the smoke test, let the smoke test be the authority (the tarball itself is already sha256-verified); record as quirk 20.

## Agenda answers

1. **Stage-3 closure: YES — close Stage 3.** Every headline claim survived adversarial reading: the parity suite really compiles and runs the TS engine against the same fixtures (`web_parity_test.mjs:30-36` compiles via `tsconfig.parity.json`, imports the emitted `engine.js`/`config.js`, asserts every `expected` key within tolerance and `deductionMethodUsed` exactly; the type-only import is elided at emit so Node ESM never trips on extensionless specifiers); the store really writes the envelope (`return_store.dart:71` + `return_format_test.dart:224-240` asserts `format=clearfile-return, version=2` **on disk**); the envelope/legacy/version-guard/migration matrix in `docs/return-format.md` matches the code in both codebases as far as I traced it; the sealed `ReturnImport` outcome replaces the silent null; the TXF caps are real in code (two of three tested — ENG-2); CI runs oracle → parity → bridges after `npm ci` with SHA-pinned actions, `contents: read`, timeouts, and working-directory correctness. The tripwire outcome was recorded honestly (box not exceeded; slip fired). Residuals ENG-1..5 are ledgered, none blocks closure — ENG-1 must clear before the RE stage's untrusted-input tooling is modeled on this parser and before any tagged release.
2. **Tripwire (web-freeze vs parity): FREEZE the TS engine now — engine + format bridges frozen at the current fixture-green state; the web app stays deployable; freeze scope = docs/security-only plus format-guard compliance (a future envelope version bump WILL require a web parser patch — state that in the freeze ADR).** Engineering argument: today every engine change costs ×2 with zero mechanical linkage between the parameter tables (ENG-6) and a triple-implemented migration (ENG-4); after a Rust core the cost is ×1 by construction; and during the transition a *third* engine under test (Dart+TS+Rust) is absurd. The TS port was executed exactly to make freezing safe: it is pinned to 16 fixtures, the format is unified (ADR-015), and the fixtures keep a frozen engine honest forever. Continuing parity means paying ×2 through a multi-quarter re-platforming window. The owner may overrule (ADR-009 prerogative) — but as a recorded decision with the doubled-cost statement re-acknowledged, not by silence.
3. **Native re-platforming settlement (ADR-014):** (i) **staged per-OS; Rust core first.** The Flutter app remains the live reference and transition vehicle — its 111-test green suite keeps something shippable at every step; big-bang leaves months with nothing shippable. Each per-OS milestone must land a working app on that OS before the next starts. (ii) **Sequencing: keep 1→3→2→4→5→6 intact; the re-platforming is a NEW gated program entered after Stage 5** (core gate → Linux → Windows → Android → macOS → web-WASM), with Stage 6 freeze closing v1. Honest constraint: macOS cannot be built or verified from this Linux sandbox at all — it goes last and needs a macOS CI runner or owner-side builds; a single maintainer running four native UIs is a multi-quarter program, so per-milestone gates keep it killable at each step without collateral damage. (iii) **Rust core scope: the 1040 engine + TXF import/export + read-only `.tax` inspection + the `.clearfile.json` codec incl. migrations + the store persistence codec. EXCLUDE the AI cascade** (network, keys, provider policy stay in the UI layer) — the core then is deterministic, offline, fixture-verifiable, and the FFI surface is a handful of functions: `compute(json)->json`, `import_txf(bytes)->json`, `export_txf(json)->bytes`, `inspect_tax(bytes)->json`, `encode/decode envelope`. The envelope IS the ABI (maximizes reuse incl. web-WASM; minimizes FFI). (iv) **Seams: one C ABI (extern "C", cbindgen header)** for Win32/Direct2D and Android-JNI; Swift consumes the same C header directly on macOS; the Linux UI is Rust so the core is just a crate — no FFI at all. (v) **macOS tiering: one AppKit UI written in Swift; "newer vs older" is a deployment-target tier (floor ≈ macOS 13), not two UIs** — language-feature availability is the variable; older-than-floor unsupported. (vi) **Linux: one toolkit — Slint** (Rust-native, GPL-3.0-compatible with this repo's GPL-3.0-only, no C++ toolchain); `gtk3-rs` only if the owner names a concrete old-distro target, else drop it. (vii) **KMP: Android-only now** (KMP gradle structure, no second target) — sharing is already the Rust core's job; a second Kotlin target with no consumer is a parallel mechanism with no payoff. (viii) **v2.0.0: yes, at the first native-stack app shipped on any OS** — the artifact set changes; the FILE format does NOT bump (envelope stays version 2; the Rust core must write bit-compatible envelopes, pinned by porting the existing return-format tests). (ix) **ADR-009 disposition: superseded when the Rust core is fixture-green + the first native UI ships** (TS freezes at agenda-2 time; Dart freezes when its last per-OS replacement ships). **Verification of a Rust core — the critical question: yes, the 16 golden fixtures become the re-platforming's regression contract (a third runner in Rust against the same JSON files, same tolerance semantics), but the fixtures alone are NOT sufficient.** A Rust port additionally needs: (a) a differential/property harness against the Dart reference on randomized + edge inputs (fixtures pin breakpoints, not the continuum — the QSS hole ENG-3 is exhibit A); (b) the bridge suites ported (TXF spec tests, `.tax` inspection incl. the malformed-ZIP crash battery from ENG-1, envelope round-trips + warning-wording — decide whether user-visible warning strings live in the core: recommend yes, so the wording contract stays pinned); (c) an arithmetic-semantics decision: port with f64 matching the reference first (no semantic changes during a port; the Python Decimal oracle stays the tiebreaker), consider cents-integer only later behind the same fixtures; (d) the fixture README's authoring discipline (never derive expected values by running any engine) carried over unchanged.
4. **Placement ADR-012: IN-REPO, with constraints.** The engineering lens decides it: the tools' verification infrastructure — SHA-pinned CI posture, `harness_check`, gitleaks, the secret guard, the gate discipline, the memory system — exists only here; a second repo owned by the same single maintainer will predictably drift ungated (no panel, no harness, no checks), and *that* is the real risk. Constraints: tools live in a clearly-labeled `re/` tree whose README restates §7; fixtures synthetic-only or gitignored owner-authored with the synthetic/owner provenance distinction CI-checkable; a no-binary-blob assertion in `hygiene.yml`; tooling never referenced from `release.yml` artifact paths (add a harness_check grep); every new job follows the SEC-1 posture.
5. **DoD fix: N = 4 published `docs/formats/` specs + a two-working-session time-box, matched to the corpus that provably exists.** (1) `tax.md` — the modern `.tax` container shape from the public write-up, upgraded with Phase-1–2 tooling output if the owner supplies an owner-authored file; (2) `clearfile.json` family — envelope v2 + v1 + legacy flat + `.cfr` alias (consolidating `docs/return-format.md` into the Phase-5 template); (3) the `.tax`-extension exchange container; (4) ClearFile's TXF v042 profile as consumed/emitted. Hard rules: any extension with zero available samples gets NO spec (honest limit — the owner's TurboTax file count is unknown to the repo, so N deliberately does not depend on them); the owner should state the owned corpus (product/version/year/count) in the ADR-012 record so N is real; if owner-authored file pairs are provided, the Phase-3 differential tooling must actually run on them and the spec gains a "verified on owner corpus" line. 6. **RE tooling security contract — operational definitions for the exit gate to verify by reading code + tests:** *write-free* = every file open is read-only (`File.readAs*` / O_RDONLY only; grep the tool tree for write/append modes and for shell-outs that write — no `unzip` extraction to disk, in-memory ZIP parsing like `tax_inspect.dart` already does; no temp files except mktemp in a designated scratch dir; never write into the input's directory) + a test running the tool on a read-only-mounted/chmod'd fixture dir asserting no new files. *resource-bounded* = up-front size refusal (TXF-style caps), bounded parse structures (entry/record/line caps — **all** of them, each with a refusal-on-oversize test asserting a clean refusal message and non-zero exit, not a crash), bounded extraction buffers (cap bytes read per entry), per-file wall-clock timeout in the driver, CI job timeout as backstop. *crash-safe* = a malformed-input battery (truncated headers, fields past EOF, adversarial lengths — my ENG-1 crafted file is the template) asserting "the analysis reports what it could not establish", never a throw. Plus the standing posture: `permissions: read`, SHA-pinned actions, timeouts, no `pull_request_target`, fixture paths gitignored (`git check-ignore` in harness_check), tooling absent from `release.yml` (harness_check grep).
