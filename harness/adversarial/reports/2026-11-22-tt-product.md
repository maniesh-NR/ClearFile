## Findings

1. **[NOTE — positive] The framing survived the risk acceptance intact.** ADR-020 does not degrade ADR-019's product promise: "the product's interaction model stays password-gated: the user's own password is the authorization … the fixed-key layer is container transport beneath that gate, never a user-facing bypass" (DECISIONS.md:730–733). Ordering is exactly right — acceptance recorded before any implementation exists (:785–789), with the overturn and reopening mechanics that make a later "open without password" request a **reopening event, never a feature request** (:750–755, :778–780). No bypass/recovery surface exists in code, marketing, or settings today (verified by grep).

2. **[MAJOR] T4's save path has no recorded data-fidelity rule — the product's biggest unmodeled risk on real user data.** The promise is read/**edit/save** of the user's real prior-year return; the engine is self-described demonstration-grade (README.md:106–125: no AMT, no Schedule SE, summary-level phase-outs). If T4's save recomputes or drops fields the engine doesn't model, ClearFile silently corrupts a real return — a data-loss failure mode on exactly the files the bridge legitimizes. ADR-019/020 and ROADMAP T4 say nothing about round-trip fidelity for unmodeled fields. T4's design must state a preservation rule (fields outside the engine's model round-trip verbatim; never silently recomputed or dropped) and the ship-time disclosure must say what the engine can and cannot compute on an edited return.

3. **[MAJOR] Stage-2 starvation has no tripwire.** Stage-2 execution session 1 (with the ADR-012/LEGAL-1 mechanics, the security-contract tools, and the first DoD spec) has been standing since 2026-11-17 while two consecutive owner-directed sessions (pstack ADR-018, TT T1 ADR-019) preempted it — and the TT program will now consume T2–T4 sessions beside it. Owner prerogative is a recorded principle, but the roadmap's own precedent (the web-freeze tripwire, ROADMAP.md:42–57) exists precisely for this class of slippage; there is no outer clock forcing Stage-2's box to ever start. Single-maintainer reality says parallel programs only resolve if the gated pipeline has a starvation alarm.

4. **[MINOR] README/SECURITY statements become false at T4 and must be replaced, not contradicted.** README.md:195 ("ClearFile does not decrypt Intuit files — no keys, no ready-made decryptors") is today's honest posture and ADR-013's superseded-in-part posture (:770–773); once T4 ships it is simply wrong unless rewritten. SECURITY.md's disclosed-posture list (:30–45) has no line for the bridge/key module. ADR-020's ship-time disclosure is recorded (:794–798) but the *replacement* of the existing statement should be explicit — an inaccurate disclosure is worse than none.

5. **[MINOR] No Intuit non-affiliation disclaimer exists today.** Nominative-descriptive naming ("TurboTax-format import") is used correctly throughout README, and the not-IRS disclaimer is prominent — but nothing states non-affiliation/trademark ownership. Nominative fair use is strengthened by exactly this disclaimer; it belongs in the ship-time provenance statement.

6. **[MINOR] §7.4's no-screenshots rule is scoped to "from proprietary binaries" — the UI study gap.** §7.4 (protocol:234–237) bans screenshots from binaries; a UI-layout study naturally produces screenshots of the *running* proprietary UI, which a future session could rationalize as outside the letter of the rule. The phase-1 notes scope the study correctly as text-only functional structure (:112–115), but the repo rule should say so explicitly before the study starts.

7. **[MINOR] "No open-without-password mode" (ADR-020 :752–753) is ambiguous as written.** The modern `.tax` family's base encryption is the fixed-key layer, not a user password (protocol §5) — files exist with no user password. Read literally the condition either forbids opening legitimately unprotected files or invites a fake password prompt (security theater, worse than honesty). Intended meaning is plainly "no mode that opens a *protected* file without its password," and the handling of the user's own unprotected files (possession-as-authorization, the TXF-import analog) should be recorded as a deliberate product decision at T4 design time.

8. **[MINOR] Spec namespace collision risk between the two parallel programs.** T3's format-family specs follow §6's `docs/formats/` convention; Stage-2's DoD check counts `docs/formats/*.md ≥ 4` with four *named* files (ROADMAP.md:205–223), one of which — `tax-modern.md`, "shape level — crypto by existence only" — is the same family T3 documents deeply. The DoD-not-grown statement exists three times over (ROADMAP:497, ADR-019:684–686, ADR-020:776–777), but the *counting/namespace* rule for a shared directory written by two parallel programs is not stated; TT specs must never count toward N=4 and the `tax-modern.md` relationship must be an explicit supersession or distinct file.

9. **[NOTE] Exit ramp is recorded for the bridge, derivable for T2/T3.** ADR-020's enforcement-response plan pauses the bridge's *distribution* and re-opens at a gate (:766–769); T2/T3 outputs are by-existence documentation (no key values per amended §7.3) and survive as research/notes on revocation — but the artifact-class split is implied, not written. One recorded line closes it.

10. **[NOTE — positive] T2 creates standalone value even if T4 never ships.** The T1 record already demonstrates it: the container map, record-table format, and eventual T3 specs serve the protocol's public-format documentation mission (§6) independent of any bridge — the same argument that carried the fixtures-first rule (ROADMAP.md:47–49). The program's research legs are sunk-cost-safe; the risk concentrates in T4, which sits behind later review.

## Verdict

**PROCEED-WITH-CONDITIONS** — the TT program's gated execution (T2, with T3/T4 shapes per ADR-020) opens.

The serious product risks attach to **T4**, not T2 — conditions 2–5 bind before T4 ships; conditions 1, 3, 6 bind now or at T2/T3 start.
